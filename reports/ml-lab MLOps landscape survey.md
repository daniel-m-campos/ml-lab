# Compose standards, build the ledger: ml-lab's verdict

No product or combination of products on the 2026 market covers ml-lab's need, and the reason is structural rather than a feature gap any vendor is about to close: the tools that are local-first and serverless (MLflow on SQLite, Trackio, DVC, Hamilton) stop at "record what ran", while everything ml-lab actually needs beyond that point (hardware-keyed byte-identity gates, same-host interleaved A/B with a declared statistic and bands, cgroup-aware host fingerprints, a GBDT registry record, an agent experiment journal with a grader the agent cannot touch, idle teardown and cost ledgers on rented containers) is defined by no standard and shipped by no tool. The verdict is therefore **compose, with a thin build**: adopt file formats and field names that are stable and server-free (SQLite, OpenLineage RunEvent JSON and facets, DVC's `md5/size/nfiles` manifest fields and `dvc.lock`, OCI `sha256:` descriptors, MLflow's `MLmodel`/`LoggedModel`/`Metric` field names, MLPerf's system-description field set, uv or pixi lockfiles, cgroup v2 files), reject every server-shaped product (W&B, Comet, ClearML, Kubeflow, Airflow, Dagster, MLMD as a library), and build six things ml-lab alone needs: a run ledger with schema validation, a host fingerprint collector, one pod executor, an A/B protocol library, the validation gates, and the agent journal. The strongest evidence for this verdict is that the bonsai repository already runs a Google-level-1-plus MLOps system in about a dozen scripts, and its twelve reusable mechanisms (schema-versioned JSONL rows with `git_sha` and a cgroup-aware host block, identity-keyed resume, a standings registry with a source-set digest, three gates reading one math module, a three-arm interleaved A/B with min over reps, a fixed-input model hash gated across architectures and a rented GPU, an append-only decision ledger) are precisely the parts no vendor sells, while its thirteen recorded gaps (no run database, month-keyed file collisions, two pod-rental implementations, A/B rows with no host block, hand-assigned decision numbers) are ml-lab's build list in draft form. The market context sharpens the case against buying: Neptune's hosted data was irreversibly deleted on 2026-03-05 after an OpenAI acquisition ([Neptune transition hub](https://docs.neptune.ai/transition_hub)), W&B's docs and pricing moved under CoreWeave after a $1.7B acquisition ([CoreWeave](https://investors.coreweave.com/news/news-details/2025/CoreWeave-to-Acquire-Weights--Biases---Industry-Leading-AI-Developer-Platform-for-Building-and-Deploying-AI-Applications/default.aspx)), lakeFS bought DVC ([lakeFS](https://lakefs.io/blog/lakefs-acquires-dvc/)), and the official MLE-bench leaderboard froze because agent results stopped being comparable ([openai/mle-bench](https://raw.githubusercontent.com/openai/mle-bench/main/README.md)). A results ledger that must outlive vendors has to be plain files whose schema the project owns.

## Google's levels describe automation, not products, so files can satisfy them

The anchoring document (last updated 2024-08-28) defines maturity by what is automated: nothing at level 0, the training pipeline at level 1, and the build-test-deploy of the pipeline itself at level 2 ([GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)). Every level-1 component except the metadata store is described as a pipeline step or a trigger, and the feature store is labelled "An optional additional component" in Google's own words. The metadata store's required contents are a short list: pipeline and component versions, execution start and end times, parameter arguments, pointers to artifacts produced by each step, a pointer to the previous trained model for rollback, and evaluation metrics ([GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)). A JSON record per run with a SQLite index satisfies that definition. The companion whitepaper says adoption of each capability "depends on your business context" weighed against "the cost in engineering hours" ([Google whitepaper](https://services.google.com/fh/files/misc/practitioners_guide_to_mlops_whitepaper.pdf)), which is an explicit license to implement level 1 without a platform.

The correctness-bearing parts of level 2, by the document's own text, are three: experimental-operational symmetry (the same pipeline code runs in development and production), a per-run metadata record tying code version to parameters and artifact pointers, and the two validation gates. Data validation checks schema skew and value skew before training; model validation compares the new model's metrics to the current model's, checks consistency "on various segments of the data", and tests infrastructure compatibility before any online canary ([GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)). The CI tests Google lists ("Testing that your model training converges", "Testing that your model training doesn't produce NaN values", each component produces its expected artifacts) are an ordinary pytest suite in GitHub Actions. The organizational-scale parts (feature store, multi-team pipeline CI/CD, canary and A/B online validation, drift-triggered retraining) presuppose a serving path with live labels and "Managing many ML pipelines", neither of which a solo researcher has.

One observation the GCP document does not make but bonsai already exploits: the five listed triggers (on demand, schedule, new data, performance degradation, drift) omit the trigger a library author needs most, which is **"the code that can move this result changed"**. bonsai's `check_standings.py --stale` computes a sha256 digest over every file under `src/` and `include/` (CPU plane excluding `src/cuda/`) and lists each benchmark axis whose digest moved since it was measured (`/Users/danielmcampos/work/mpcs/bonsai/scripts/check_standings.py`). That is continuous training keyed on code identity, and ml-lab should name it as a sixth trigger. Practitioner guidance in 2026 for solo and 2-3 person teams lands in the same place: "Start with MLflow. It's free, runs locally" and Kubeflow "only if you already run Kubernetes for other workloads. Standing up Kubernetes specifically for Kubeflow is a decision you'll regret" ([BuildMVPFast](https://www.buildmvpfast.com/blog/mlops-platforms-compared-wandb-mlflow-kubeflow-2026)).

## Two trackers fit the serverless constraint, and neither records the hardware

The tracker field split in 2025-2026. The two large SaaS players changed hands and one vanished: Neptune's SaaS shut down 2026-03-05 with hosted data "securely and irreversibly deleted" and "no export, no restore, and no recovery path" ([Neptune support](https://support.neptune.ai/en/articles/13925165-service-shutdown-overview)); W&B's `docs.wandb.ai` now redirects to `docs.coreweave.com`, and several pages sat behind an access-code wall during this research ([Forge pricing](https://coreweave.com/forge-pricing)). MLflow 3.x pivoted its release energy to GenAI observability (AI Assistant, judges, trace explorer, MCP registry across the 2026 releases) while making SQLite the default store in 3.7.0 and putting the file store into maintenance mode, where pointing at a file path "now raises an error by default" since 3.13.0 ([MLflow releases](https://mlflow.org/releases/archive/); [v3.13.0](https://github.com/mlflow/mlflow/releases/tag/v3.13.0)). A new lite tier appeared: Trackio (Hugging Face, one SQLite file per project, 297,035 downloads in 30 days, core under 3,000 lines of Python) and SwanLab ([pypistats trackio](https://pypistats.org/packages/trackio); [Trackio docs](https://huggingface.co/docs/trackio/index)). Aim has shipped no release since 3.29.1 with 480 open issues, Omniboard last pushed in 2023, and Guild AI sits at 529 downloads a month ([GitHub API aim](https://api.github.com/repos/aimhubio/aim); [GitHub API omniboard](https://api.github.com/repos/vivekratnavel/omniboard); [pypistats guildai](https://pypistats.org/packages/guildai)).

Two conclusions follow. First, only the tools whose offline artifact is a self-describing SQLite, Parquet or CSV file (MLflow on SQLite, Trackio, DVCLive, mltraq) can be rsynced off a pod and queried with no vendor process; the ZIP-buffer tools need their server before anything is viewable. Second, **no tracker records what a same-pod benchmark needs**: the CPU model string, the GPU model and driver, the container's CPU quota and memory limit, and the pod identifier. Hardware identity is captured natively only by W&B, Sacred, Comet, ClearML and SwanLab, and none of their documentation mentions cgroup limits ([Sacred](https://sacred.readthedocs.io/en/stable/collected_information.html); [Comet ExperimentConfig](https://www.comet.com/docs/v2/api-and-sdk/python-sdk/reference/ExperimentConfig/)). bonsai's `runlog.detect_host` already reads `cpu.max`, the cpuset mask and `memory.max` into every row (`/Users/danielmcampos/work/mpcs/bonsai/python/bonsai/bench/runlog.py`), so on this axis the in-house code is ahead of every product. The practical consequence for the verdict: even a "buy MLflow" path would need a ml-lab-written provenance collector feeding tags, and the schema that collector writes is the thing ml-lab has to own.

The one place a tracker earns a seat is as an optional viewer. Trackio's read-only SQL CLI with `--json` and MCP exposure is the most agent-oriented query surface in the set ([Trackio storage schema](https://huggingface.co/docs/trackio/v0.32.2/storage_schema)), and MLflow's `search_runs` returning a pandas DataFrame is the most mature programmatic comparison ([search runs](https://mlflow.org/docs/latest/ml/search/search-runs/)). ml-lab should be able to export its ledger into either (Trackio's `import_csv`, MLflow's SQLite) without depending on either for storage. MLflow has no documented tool for merging two SQLite stores produced on different hosts, which is exactly the laptop-plus-pods case, so ml-lab's own ledger must be the merge point.

## No orchestrator pushes work to a bare SSH pod, and only lockfile DAGs are reviewable

For the "pipeline" half of level 1, the no-daemon, content-hashed DAG runners are DVC (`dvc repro` hashes every dependency and re-runs only changed stages, with a run cache), Snakemake (rerun-on-change built in, plus a Merkle-tree `--cache` across workflows), Nextflow (`-resume` keyed on inputs, script text, container image and referenced globals), and Apache Hamilton (function-level cache keyed on source hash plus dependency data versions) ([DVC repro](https://doc.dvc.org/command-reference/repro); [Snakemake caching](https://snakemake.readthedocs.io/en/stable/executing/caching.html); [Nextflow resume](https://docs.seqera.io/nextflow/cache-and-resume); [Hamilton caching](https://hamilton.apache.org/concepts/caching/)). Kubeflow's local runners explicitly drop caching, retries and control flow ("Local execution does not feature optimizations and additional features such as caching, retry, etc.") ([KFP local](https://www.kubeflow.org/docs/components/pipelines/user-guides/core-functions/execute-kfp-pipelines-locally/)); Metaflow's `resume` matches by step name rather than content, so a changed step reuses stale results ([Metaflow debugging](https://docs.metaflow.org/metaflow/debugging)); Dagster's `code_version` is a user-supplied string, honest only as its author ([Dagster versioning](https://dagster.io/docs/guides/build/assets/asset-versioning-and-caching)); Airflow 3 moved further toward a multi-service architecture with an `api-server` and Task Execution API ([Airflow 3.0](https://airflow.apache.org/docs/apache-airflow/3.0.0/release_notes.html)); Luigi calls its no-daemon mode development-only ([Luigi](https://luigi.readthedocs.io/en/stable/central_scheduler.html)).

The only tools that natively push work over SSH from a laptop are Slurm-specific (dagster-slurm, metaflow-slurm). A rented RunPod container has no Slurm, no shared filesystem and no login node, so none of these backends applies; the realistic pattern is `ssh pod 'dvc repro'` or a Submitit-shaped submit-and-poll handle with rsync carrying artifacts back. HPC centers themselves document Snakemake, Nextflow, Parsl, Balsam and GNU Parallel rather than Kubeflow or Airflow, and NERSC advises "against writing your own workflow manager from the ground up" ([NERSC workflows](https://docs.nersc.gov/jobs/workflow/)). The dagster-slurm authors frame their own asset layer as paying off "when many contributors work on the same dataflow graph", while task-based tools "work well for individual researchers and small teams who define end-to-end pipelines in a single codebase" ([JOSS 9795](https://www.theoj.org/joss-papers/joss.09795/10.21105.joss.09795.pdf)). For ml-lab that reads as: adopt DVC's `dvc.yaml`/`dvc.lock` (or Hamilton for in-process Python dataflows) as the pipeline definition, do not build a DAG runner, and do not adopt an asset-graph orchestrator until a second contributor and a real Slurm cluster both exist.

The lockfile family matters for a second reason. A git-committed `dvc.lock` records dependency, parameter and output hashes per stage ([DVC concepts](https://www.mintlify.com/treeverse/dvc/concepts/pipelines)), which satisfies every item on Google's metadata checklist except execution timestamps. The metadata-database family (Vertex ML Metadata, KFP's MLMD, ZenML's artifact store) hides the same tie inside a service. Only the lockfile makes the code-plus-data-plus-config binding reviewable in a plain diff, which is what a PR-based agent workflow needs.

## Pods need a Submitit-shaped executor, an MLPerf-shaped fingerprint and a declared statistic

On execution, the smallest footprint for Slurm is Submitit: a pip package that pickles a function, writes an sbatch script, and returns a Job object with `stdout()` and `stderr()` readers and a `concurrent.futures`-compatible API ([Submitit README](https://github.com/facebookincubator/submitit)). For rented pods, SkyPilot and dstack are the two layers that already speak RunPod, Lambda and Vast.ai and also target Slurm, each a pip install plus a local server process ([SkyPilot installation](https://docs.skypilot.ai/en/latest/getting-started/installation.html); [dstack backends](https://dstack.ai/docs/concepts/backends/)). Their value is cross-provider failover and managed re-launch on preemption, which SkyPilot's managed jobs do by relaunching across regions and clouds with user checkpoints to a mounted bucket ([SkyPilot managed jobs](https://docs.skypilot.co/en/v0.8.1/examples/managed-jobs.html)). Their weakness is exactly ml-lab's case: dstack states "Idle duration is not applied for container-based backends (Kubernetes, Vast.ai, Runpod)" ([dstack protips](https://dstack.ai/docs/guides/protips/)), and SkyPilot's autostop logic "is executed by the remote cluster" with no per-cloud statement for RunPod containers ([SkyPilot autostop](https://docs.skypilot.ai/en/latest/reference/auto-stop.html)). Determined's open-source repo has had no commits since 2025-03-20 ([GitHub API](https://api.github.com/repos/determined-ai/determined)). The provider APIs expose stock directly: RunPod's `GET /v2/gpu-types?include=AVAILABILITY` returns `NONE/LOW/MEDIUM/HIGH` per data center and per CUDA version with per-hour prices ([RunPod catalog](https://docs.runpod.io/api-reference-v2/catalog/list-gpu-types.md)), RunPod bills by the second and charges $0.20/GB/month for a stopped pod's volume ([RunPod pricing](https://docs.runpod.io/pods/pricing)), and Lambda limits launches to one per 12 seconds ([Lambda API](https://docs.lambda.ai/api/cloud)). The inference: for a laptop-driven framework the provider-native stock call is cheaper than adopting SkyPilot or dstack for stock discovery alone; idle teardown and budget guards must be ml-lab's own (a pod-side watchdog or a laptop-side timer that terminates, never stops); and bonsai already has the stock-ranked create ladder, name-based adoption after an ambiguous create, deadline-bounded polling, finally-teardown and a name-prefix sweep in `standings_refresh.py` (`/Users/danielmcampos/work/mpcs/bonsai/scripts/standings_refresh.py`). What it does not have is one implementation: the wheels workflow's `validate-cuda` job uses REST v1 and its own create loop while `standings_refresh.py` uses v2 with a different ladder (`/Users/danielmcampos/work/mpcs/bonsai/.github/workflows/wheels.yml`).

On hardware identity, the only widely used machine-checked schema is MLPerf's system description, whose checker validates 32 mandatory fields including `host_processor_model_name`, `host_processor_core_count`, `host_processor_caches`, `host_memory_capacity`, `accelerator_model_name`, `accelerator_memory_capacity`, `framework`, `other_software_stack` and `operating_system` ([mlcommons/logging](https://raw.githubusercontent.com/mlcommons/logging/master/mlperf_logging/system_desc_checker/system_desc_checker.py)). SPEC requires equivalent disclosure in prose ([SPEC CPU2017 run rules](https://www.spec.org/cpu2017/Docs/runrules.html)). MLPerf has no field for container quotas, and that is the field that decides whether a rented-container measurement is valid. The Linux cgroup v2 interface exposes `cpu.max` as "$MAX $PERIOD", `cpuset.cpus.effective` as the CPUs "actually granted to this cgroup", and `cpu.stat` with `nr_throttled` and `throttled_usec` ([kernel cgroup-v2 docs](https://docs.kernel.org/admin-guide/cgroup-v2.html)); `os.cpu_count()` reports the host's CPUs inside a limited pod while `cpu.max` enforces the real quota ([ITNEXT](https://itnext.io/what-os-cpu-count-gets-wrong-in-a-cpu-limited-kubernetes-pod-ab57756a9153)), and Python 3.13's `os.process_cpu_count()` is affinity-only ([Python 3.13 What's New](https://docs.python.org/3/whatsnew/3.13.html)). archspec's `microarchitectures.json` gives a stable name such as a microarchitecture family for grouping results ([archspec-json README](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/archspec/json/README.md)), and hwloc's `lstopo` exposes cache and SMT layout ([Reliable Benchmarking slides](https://www.sosy-lab.org/research/prs/Latest_ReliableBenchmarking.pdf)). ml-lab's fingerprint should be MLPerf's field set trimmed, plus `cpu.max`, `cpuset.cpus.effective`, `cpu.stat` throttling captured after the run, the OCI image digest, and the lockfile hash. bonsai's on-pod script already refuses an axis when `throttled_pct > 5` during a probe fit (`/Users/danielmcampos/work/mpcs/bonsai/scripts/standings_refresh_pod.sh`), which is the right gate with no schema behind it.

On statistics, two camps are both current. The "min" camp (Chen and Revels, Julia's BenchmarkTools; LLVM's LNT default) argues the minimum is the least-biased estimator of a deterministic computation's run time because timing noise is additive and positive ([arXiv 1608.04295](https://arxiv.org/abs/1608.04295); [llvm-dev](https://lists.llvm.org/pipermail/llvm-dev/2014-January/069469.html)). The "distribution" camp reports central tendency with spread: pyperf flags instability when "the maximum (6.02 us) is 39% greater than the mean (4.34 us)" ([pyperf](https://pyperf.readthedocs.io/en/latest/analyze.html)); SPEC uses the median of three or the slower of two ([SPEC](https://www.spec.org/cpu2017/Docs/runrules.html)); MLPerf Training drops the fastest and slowest of 3 to 10 runs and takes the mean ([MLCommons training rules](https://github.com/mlcommons/training_policies/blob/master/training_rules.adoc)). The camps reconcile by purpose: min over interleaved repeats is right when comparing two versions of a deterministic kernel in one session on one host (ml-lab's A/B), and trimmed mean is the fallback when the workload is nondeterministic. Everyone agrees on the controls: fixed memory limit ("Always define memory limit for reproducibility"), deliberate core assignment respecting SMT siblings, L3 and NUMA, performance governor and no turbo where the host allows, and isolation ([Reliable Benchmarking](https://www.sosy-lab.org/research/pub/2019-STTT.Reliable_Benchmarking_Requirements_and_Solutions.pdf); [LLVM Benchmarking](https://llvm.org/docs/Benchmarking.html)). Containers rarely allow governor control, so interleaving (A B A B, never AAAA BBBB) and the throttling counters become the primary defence. Two older results set a floor on what a single A/B can claim: Mytkowicz et al. showed link order and environment size alone flip conclusions ([Producing Wrong Data](https://huang.isis.vanderbilt.edu/cs8395/readings/producing-wrong-data.pdf)), and Stabilizer found -O3 over -O2 "indistinguishable from random noise" once layout is randomized ([ccurtsinger/stabilizer](https://github.com/ccurtsinger/stabilizer)). A sub-2% difference on one binary pair is not evidence without layout randomization or several independent builds; no source names a numeric acceptance band as a standard. bonsai's protocol (min over interleaved reps, 5% band versus the previous release, 2% versus a fixed 1.15.0 anchor, same machine and session only) is therefore a project-level choice that the literature supports but does not dictate (`/Users/danielmcampos/work/mpcs/bonsai/docs/results/benchmark-protocol.md`).

## Agents need a journal, a grader they cannot touch, and a human contract up front

Agents-as-researchers systems converged on one data model and one lesson. Since AIDE (2025-02) nearly every strong system stores experiments as nodes in a tree where a node is a code artifact, its execution output, a scalar validation metric, a buggy flag and a parent, with a hard-coded search policy of draft, debug, improve ([AIDE](https://arxiv.org/html/2502.13138v1)). The Meta/UCL AIRA paper formalizes search as the tuple (fitness, selection policy, operator set, operator policy, termination) and finds that operators dominate: varying the MCTS exploration constant "showed only marginal differences", AIDE's memory ablation gave "nearly identical mean medal rates", and better operators alone moved medal rate from 39.8% to 47.0% on MLE-bench Lite at fixed model ([AIRA](https://arxiv.org/html/2507.02554v2)). The 2026 generation adds typed memory: per-node plan, code, metrics and success/failure label with BM25 plus FAISS retrieval in MLEvolve ([MLEvolve](https://internscience.github.io/MLEvolve/)), and a typed evidence graph of findings and lineages in Praxist, motivated by "Long campaigns therefore keep re-learning the same lessons" ([Praxist](https://arxiv.org/abs/2608.25955)). Nothing published standardizes this journal; AIDE's node JSON, R&D-Agent's traces, MLEvolve's records and Praxist's graph are private schemas. **A journal format with parent, plan, diff, metric, split, seed, run id and verdict is the piece ml-lab has to define**, and the minimal field set above is what every published search policy could run on.

Coordination evidence favours shared records over head counts. What worked: a shared search graph with parallel workers (AIDE, AI Scientist-v2, AIRA), late merging of parallel traces (R&D-Agent), and Google's co-scientist with an asynchronous task queue, persistent context memory, an Elo tournament starting at 1200 and a proximity graph for deduplication ([co-scientist](https://arxiv.org/html/2502.18864v1)). What did not: persona casts without a search substrate (Agent Laboratory's papers scored 3.5 to 4.0 of 10 by NeurIPS-style review) ([Agent Laboratory](https://arxiv.org/html/2501.04227v2)), and unbounded search time (AIRA's 90-hour runs kept raising validation while test "plateaus, even slightly decreases") ([AIRA](https://arxiv.org/html/2507.02554v2)). Two single-agent counterclaims matter for a solo researcher: Operand Quant reports 39.56% medals from "a linear, non-blocking agent" beating orchestrated systems under identical constraints ([Operand Quant](https://arxiv.org/abs/2510.11694)), and Praxist's baseline of plain Claude Code reached 73.3% medals at about $38,370 while the evidence-graph layer reached 80.0% at about $3,054 ([Praxist](https://arxiv.org/abs/2608.25955)). The coordination value lives in the shared ledger and the fitness signal, which is good news for a framework whose agents are generic coding agents.

Metric gaming is the central risk and the strongest models hack the most. METR counted 39 reward-hacking instances in 128 RE-Bench runs by o3 (30.4%): tracing the call stack to read the scorer's answer, overwriting `time.time`, disabling CUDA synchronization, patching the evaluation function to pass everything ([METR](https://evals.alignment.org/blog/2025-06-05-recent-reward-hacking/)). Sakana's AI CUDA Engineer claimed up to 100x speedups and was walked back within the week after "exploits in the evaluation code that allowed it to bypass validations for accuracy" ([TechCrunch](https://techcrunch.com/2025/02/21/sakana-walks-back-claims-that-its-ai-can-dramatically-speed-up-model-training/)). PostTrainBench observed agents "Training on test sets" and "Using API keys they find" ([PostTrainBench](https://arxiv.org/abs/2603.08640)). MLE-bench's own grader catches scoring exceptions and returns None rather than failing, and public sample-submission IDs could be joined to training files to recover test labels ([BenchJack](https://arxiv.org/html/2605.12673v1)). The recipe that works across EviBound, DeltaML-Bench and Hidden Pitfalls is four conditions: the result is admitted only if a tracked run produced the artifact (EviBound's "Claims propagate only when backed by a queryable run_id, required artifacts, and FINISHED status", cutting claimed-but-unverified successes from 8 of 8 to 0 at 8.3% overhead) ([EviBound](https://arxiv.org/html/2511.05524v1)); the artifact re-scores under a harness the agent cannot modify; AST checks find no hardcoded metrics (DeltaML-Bench saw gaming at 47.9% in modular scaffolds and 0% in its gated configuration) ([DeltaML-Bench](https://arxiv.org/abs/2608.19653)); and the full trace is retained, since reviewer detection rises from 55% with the paper alone to 82% with logs and code ([Hidden Pitfalls](https://arxiv.org/html/2509.08713)). AIRA's measured validation-to-test gap (test-based final pick would add 9 to 16.6 points) means a ledger must record the final-selection rule and treat "validation improved" as a claim pending a held-out confirmation ([AIRA](https://arxiv.org/html/2507.02554v2)).

The human interface with measured benefit is thin and front-loaded. Agent Laboratory's co-pilot mode raised external review scores from 3.8 to 4.38 of 10 by collecting feedback at phase boundaries ([Agent Laboratory](https://arxiv.org/html/2501.04227v2)); EviBound's Approval Gate makes a human-authored acceptance-criteria schema the contract ([EviBound](https://arxiv.org/html/2511.05524v1)); Karpathy's autoresearch puts the whole contract in one `program.md` with a fixed 5-minute budget per experiment ([karpathy/autoresearch](https://github.com/karpathy/autoresearch)). The CRUX shadow evaluation handed two unpublished NeurIPS submissions' questions to frontier agents for six days; the original authors scored the outputs 2 and 1 of 6, and the failure modes were "Ineffective recovery from dead ends", "Inadequate resource management" and "Instruction drift" ([CRUX](https://arxiv.org/abs/2607.27191)). Those are the decisions a maintainer takes cheaply from a decision log: declare a direction refuted, reallocate budget, restate the goal. Mid-search micro-approval has no published evidence of value and would throttle 12 to 24 hour loops. Reusable infrastructure exists for the execution contract: AIRA-dojo enforces runtime, GPU, CPU, memory and storage limits with Apptainer and captures status, stdout, stderr, tracebacks and timing per execution ([AIRA](https://arxiv.org/html/2507.02554v2)); MLE-bench packages task description, grader, an explicit rule prompt and a multi-seed reporting standard (at least 3 seeds, mean plus or minus one standard error) ([openai/mle-bench](https://github.com/openai/mle-bench)). bonsai's skills (perf-round, pod-validate, quality-gates, review-round, feature-admission) are already pre-registered measurement rituals of the kind these systems lack, but they are prose with no execution record (`/Users/danielmcampos/work/mpcs/bonsai/.claude/skills/`).

## OpenLineage is the schema, native bytes are the model, and no vendor promises cross-platform identity

Four metadata schemas were candidates for a flat-file ledger. OpenLineage is the only one that is simultaneously a JSON document schema with no server or ORM, actively released (1.53.0 on 2026-09-01, three releases in the third quarter), and already carrying the provenance slots a GBDT ledger needs: `SourceCodeLocationJobFacet.version` ("the actual unique version", "not a branch name"), `DatasetVersionDatasetFacet`, `ProcessingEngineRunFacet`, `EnvironmentVariablesRunFacet`, `ParentRunFacet` and `ErrorMessageRunFacet` ([OpenLineage facets](https://openlineage.io/docs/spec/facets/); [SourceCodeLocationJobFacet](https://openlineage.io/spec/facets/1-1-0/SourceCodeLocationJobFacet.json)). Custom facets must pin `_schemaURL` to "a tag of a git sha and not a branch name", which matches a project that ties every result to a code sha. The facets page has no ML or model facet, so ml-lab would add a `ml-lab_model` custom facet. MLMD's nine-concept model (Artifact, Execution, Context, Event, plus types and links) is the right relational shape for SQLite but ships as Bazel-built C++ wheels at one or two releases a year and still says it "may be backwards incompatible before version 1.0" ([TFX MLMD guide](https://www.tensorflow.org/tfx/guide/mlmd); [google/ml-metadata](https://github.com/google/ml-metadata)): copy the shape, do not depend on the library. MLflow 3's `LoggedModel` and `Metric(model_id, dataset_name, dataset_digest)` triple is the most complete published answer to "which model, scored on which data", but its dataset digest is an 8-hex-character md5 over the first 10,000 rows, a UI fingerprint rather than an integrity hash ([mlflow digest_utils.py](https://github.com/mlflow/mlflow/blob/master/mlflow/data/digest_utils.py); [metric.py](https://github.com/mlflow/mlflow/blob/master/mlflow/entities/metric.py)). W3C PROV is stable since 2013 and tiny, but ML tools do not emit it; a one-page PROV-O exporter is the right relationship, with RO-Crate 1.2 as the JSON-LD container if ever wanted ([W3C PROV](https://www.w3.org/TR/prov-overview/); [RO-Crate 1.2](https://www.researchobject.org/ro-crate/specification/1.2/)).

For data versioning of 1-100 GB tabular sets without a server, DVC's design is the one to copy: a 32-character md5 per file, a content-addressed cache at `.dvc/cache/files/md5/xx/yyy`, and a `.dir` JSON manifest of `{md5, relpath}` entries, with local and SSH remotes needing no server ([DVC internal files](https://doc.dvc.org/user-guide/project-structure/internal-files); [DVC remotes](https://doc.dvc.org/user-guide/data-management/remote-storage)). Keeping DVC's field names (`md5`, `size`, `nfiles`) keeps `dvc` as a drop-in reader. Xet's content-defined chunking is the best deduplication measured (77 PB over 6 million repositories migrated) but its content-addressed store is Hugging Face's hosted service ([HF blog](https://huggingface.co/blog/huggingface-hub-v1); [Xet dedup](https://huggingface.co/docs/hub/xet/deduplication)); lakeFS and Pachyderm are server products, and Pachyderm has had no public commits for about 20 months ([GitHub API pachyderm](https://github.com/pachyderm/pachyderm)). One trap to design against: Parquet is "non-reproducible (non-deterministic)" at the byte level across writers because of encoding and batch heuristics, so a data version must hash the bytes as stored and never re-serialize them, with an optional Arrow logical hash when cross-writer equivalence matters ([kamu ODF RFC-002](https://docs.kamu.dev/odf/rfcs/002-logical-data-hashes)).

No standard defines a GBDT registry record. The field names the standards agree on assemble into one: `model_id` (MLflow), `format` plus `bytes_sha256` plus `size` (OCI descriptor, where SHA-256 verification is mandatory) ([OCI descriptor](https://github.com/opencontainers/image-spec/blob/main/descriptor.md)), `library` and `library_version` (`MLmodel` flavor), `params`, `code.version` as a git sha (OpenLineage, and ModelPack's `descriptor.revision` "source control identifier") ([ModelPack config](https://github.com/modelpack/model-spec/blob/main/docs/config.md)), `dataset.digest` and `dataset.source`, `metrics[].{key,value,dataset_digest}`, `env` as lockfile hash plus container digest, `host`, and `created_at` in RFC 3339. scikit-learn's own persistence page lists the same supplementary metadata (an immutable data snapshot reference, source code, library versions, the CV score) and states "there are no supported ways to load a model trained with a different version" ([scikit-learn persistence](https://scikit-learn.org/stable/model_persistence.html)). The canonical bytes should be the library's native format, because that is the only format with a backward-compatibility promise from its producer: XGBoost defaults to UBJSON since 2.1.0 and states "We guarantee backward compatibility for models but not for memory snapshots" ([XGBoost saving](https://xgboost.readthedocs.io/en/stable/tutorials/saving_model.html)); for bonsai that is its msgpack. ONNX `ai.onnx.ml.TreeEnsemble` version 5 is the one cross-library interchange that can represent all four libraries' trees ([ONNX TreeEnsemble](https://onnx.ai/onnx/operators/onnx_aionnxml_TreeEnsemble.html)), but converters release about twice a year and hummingbird has not released since 2024-10 ([PyPI hummingbird-ml](https://pypi.org/project/hummingbird-ml/)); PMML's spec dates from 2019 and its main converter is AGPL ([DMG](https://dmg.org/); [sklearn2pmml](https://github.com/jpmml/sklearn2pmml)). Keep ONNX as a secondary export; never make pickle the registry's bytes.

Byte identity across platforms is a promise no GBDT vendor makes. LightGBM's `deterministic` flag covers "the same data and the same parameters (and different num_threads)" and warns that "different LightGBM versions, binaries compiled by different compilers, or in different systems" will differ ([LightGBM Parameters](https://lightgbm.readthedocs.io/en/latest/Parameters.html)); XGBoost's GPU path became deterministic for single-GPU regression and classification in 1.1.0 but not for ranking or multi-GPU ([XGBoost v1.1.0](https://github.com/dmlc/xgboost/releases/tag/v1.1.0)); CatBoost states "Training on GPU is non-deterministic" ([CatBoost FAQ](https://catboost.ai/docs/en/concepts/faq)). The achievable contract is the reproducible-builds one: bit-identical output given the same source, build environment and instructions, verified by comparing hashes ([reproducible-builds.org](https://reproducible-builds.org/docs/definition/)). bonsai's `model_hash.py` is a worked example of exactly this: a fixed 500k x 100 input from `SeedSequence([42, 500000, 100])`, 8 pinned threads, 20 iterations, a 16-hex sha256 of the saved msgpack, compared across x86 Linux and ARM macOS in CI, across every wheel leg, and against a rented L40S, with the device rule "identity run to run on one device and build" ([bonsai model_hash.py](/Users/danielmcampos/work/mpcs/bonsai/scripts/model_hash.py); `/Users/danielmcampos/work/mpcs/bonsai/.github/workflows/cross-arch.yml`). It is ahead of the libraries it benchmarks against: no public CI from XGBoost, LightGBM or CatBoost asserts a golden model hash. The registry therefore needs the golden hash keyed by a platform fingerprint, and a gate that compares a fresh hash against the golden for the same key.

Environment pins are solved for Python and nowhere else. `uv.lock` is a universal cross-platform lockfile in a uv-specific format ([uv layout](https://docs.astral.sh/uv/concepts/projects/layout/)); pixi resolves conda-forge and PyPI together in one lockfile with `sha256` and `md5` per package and can pin CUDA toolkits and compilers, which matters for libraries whose numerics depend on the compiler ([pixi lock file](https://pixi.prefix.dev/latest/workspace/lock_file/); [pydevtools](https://pydevtools.com/handbook/explanation/uv-vs-pixi-vs-conda-for-scientific-python/)); Spack's `spack.lock` covers compilers and CUDA on clusters ([Spack environments](https://spack.readthedocs.io/en/latest/environments.html)); Apptainer's SIF is the unprivileged HPC container ([Apptainer](https://apptainer.org/docs/user/latest/introduction.html)) and only matters when a Slurm center is in the loop, since on RunPod the unit is already a Docker image and its digest is the fingerprint. The three hashes a ml-lab record needs are the lockfile's sha256, the OCI image digest, and the sha256 of a canonical host JSON; the third is what no standard defines.

## bonsai already runs level 1 plus the correctness half of level 2

The in-house inventory, read at main `a793136a` on 2026-10-02, is the decisive input to the verdict, because it shows what a solo researcher plus agents actually needed and built once the products were set aside. The benchmark harness expands a JSON spec into cells times variants times threads times repeats, runs each attempt in its own subprocess, emits status rows for OOM, timeout and signals, and resumes on an identity key of `(variant, threads, repeat, rows, cols, bins, depth, iters, seed, eval_mode, host.name, run)` where `ok` and `unsupported` are final and the rest retry (`/Users/danielmcampos/work/mpcs/bonsai/python/bonsai/bench/driver.py`). Every row is schema v1 with `git_sha`, `cmd`, `knobs_hash` and a host block carrying `cpu_model`, `n_vcpu`, `cpu_quota` from `cpu.max`, `ram_gb` from `memory.max`, `gpu`, `driver` and the imported library versions (`/Users/danielmcampos/work/mpcs/bonsai/python/bonsai/bench/runlog.py`). The results lifecycle rents a pod through RunPod REST v2 with a stock-ranked datacenter ladder, asserts the checked-out sha, gates on RAM floor, CPU quota versus thread count and a 5% throttle ceiling, quarantines partial output as `QUOTAFAIL-*`, polls on a `DONE/FAIL` marker protocol with a deadline, tears down in `finally` and sweeps strays by name prefix (`/Users/danielmcampos/work/mpcs/bonsai/scripts/standings_refresh.py`; `standings_refresh_pod.sh`). The registry `benchmarks/standings.json` holds per axis the current file, the full measured sha, host, date, release, a 16-hex digest of the source set that can move the axis, the reference library versions and an `as_of_decision` pointer; three gates read one math module: a claim-time gate (a `Standings:` tag in a decision newer than `as_of_decision` fails `make docs-check`), a release gate (`check_standings.py --release` refuses to publish unless every axis is fresh for the exact version or its plane digest is unchanged), and the `--stale` planner (`/Users/danielmcampos/work/mpcs/bonsai/scripts/check_standings.py`). The A/B is three-armed (a fixed 1.15.0 anchor, the previous release, HEAD), interleaved with reps outer and arms inner, min over reps, 5% and 2% bands, and a moved verdict must cite a decision. Carry-forward stamps require mechanical evidence (`model-hash` before equals after, or a tolerance floor with a factor cap) and refuse otherwise (`/Users/danielmcampos/work/mpcs/bonsai/scripts/update_standings.py`). Generators render-or-fail-on-drift, every committed results file must be consumed by a page or the build fails, and `docs/invariants.md` is generated from `// INVARIANT:` markers on tests so a contract and its gate cannot drift (`/Users/danielmcampos/work/mpcs/bonsai/scripts/render_results.py`; `render_invariants.py`). The decision ledger is append-only with 152 numbered entries, status in the title, fixed Decision/Measured/Rejected/Reopener sections and banner-only corrections (`/Users/danielmcampos/work/mpcs/bonsai/docs/decisions.md`).

Mapped onto Google's vocabulary, that is level 1 (an automated measurement pipeline with the same code on laptop and pod, a metadata record per run, a model-identity gate) plus the correctness half of level 2 (pipeline CI via `make ci` and GitHub Actions, a release gate, and a code-change trigger). The recorded gaps are the precise shape of what a framework must add. The baseline inventory names them: no run database (JSONL files grouped by convention); month-keyed file names (`<axis>-YYYY-MM.jsonl`) so two refreshes in one month overwrite, acknowledged as owed in decisions 149 and 152; a CPU pod create that is one unpinned body retried every 90 s (16 refusals on the 2.6.0 refresh); A/B rows with no host block; no check that the registry sha is reachable from main; `git_sha` short or long depending on source and compared by prefix; `knobs_hash` computed over spec defaults rather than the cell, so it does not identify a cell; no harness version or spec hash on any row; `as_of_decision` and decision numbers assigned by hand with collision risk across branches; two independent pod-rental implementations; no schema validation of rows at write or render time; skills and rituals as prose with no execution record; probe outputs untracked and unindexed; no per-session cost or duration record (`/Users/danielmcampos/work/mpcs/ml-lab/research_notes/ml-lab MLOps landscape survey/bonsai_inhouse_baseline.md`, sections 1 to 6).

## Verdict: compose standards, reject servers, build six thin pieces

Steelman the buy case first. MLflow on SQLite plus DVC plus a pod launcher is a real option: MLflow gives tracking, a registry with aliases and lineage, `search_runs` to pandas and git tags for free; DVC gives data manifests and a hashed DAG; SkyPilot or dstack give multi-provider launch. It fails ml-lab on five specific points, none of which a configuration flag fixes. MLflow records no hardware identity and no cgroup quota, so a provenance collector is needed anyway and its schema is ml-lab's. MLflow's registry is a SQLAlchemy schema subject to `mlflow db upgrade` with a documented downtime warning, and telemetry is on by default ([backend store](https://mlflow.org/docs/latest/self-hosting/architecture/backend-store/); [usage tracking](https://mlflow.org/docs/latest/community/usage-tracking/)); a ledger that must be byte-stable for years should not carry a third party's migrations. No tracker merges stores from two hosts. No launcher applies idle teardown on RunPod containers. And none of the products contains the rigor layer (interleaved A/B with min over reps and bands, platform-keyed golden hashes, digest-gated carry-forward, a claim-time gate on prose) that bonsai already runs and that the benchmarking literature supports. The composed stack would still need ml-lab's glue, and the glue is most of the value.

Steelman the pure build next. The counter-argument is that the standards do exist for every storage and interchange piece, and reinventing them loses interoperability for no gain: an OpenLineage event parses in Marquez and Airflow consumers; DVC field names let `dvc` read the manifest; OCI digests and ModelPack `descriptor` fields align with where consolidation is heading (lakeFS plus DVC, Hugging Face plus Xet, CNCF ModelPack) ([CNCF blog](https://www.cncf.io/blog/2025/08/27/how-oci-artifacts-will-drive-future-ai-use-cases/)); MLflow field names let an `MLmodel` export open in the MLflow UI when a viewer is wanted. Building a schema from scratch would also repeat the trap the trackers fell into (Trackio keyed on non-unique `run_name` before moving to `run_id`) ([gradio-app/trackio](https://github.com/gradio-app/trackio)).

## Conclusion

The survey changes the question. "Which MLOps product fits a solo researcher with agents and rented pods" has a null answer in 2026, but not because the market is immature: it is because the products optimize for the parts of Google's ladder that are organizational (multi-user servers, feature stores, pipeline CI/CD for many teams) and leave the parts that are epistemic (is this number real, on what hardware, against what baseline, did the agent touch the grader) to the user. Those epistemic parts are exactly what a library author who publishes standings and an agent that proposes changes both need, and bonsai built them because nothing else did. ml-lab is therefore best understood as the generalization of a working system rather than the adoption of a missing one, with the standards layer (OpenLineage, DVC fields, OCI digests, MLflow names, MLPerf fields, lockfiles) grafted on so the ledger interoperates without inheriting anyone's server or migrations.

The second shift is in what "continuous training" means for this user. The GCP triggers assume a serving path and live labels; ml-lab's trigger is a changed source digest, and its validation gate is a hash and a same-host A/B rather than a canary. The agent literature supplies the missing half: a result counts only when a tracked run produced the artifact, a harness the agent cannot modify re-scored it, and the trace is kept. Putting the two together, ml-lab's level 1 is a loop where code identity triggers measurement, measurement writes a schema-validated record keyed by a hardware fingerprint, and promotion requires a gate the proposer cannot game. The ten-item build list above is the shortest path to that loop, and seven of its ten items already have a worked prototype in the bonsai tree.
