# ML pipeline orchestration and CT/CI-CD tooling (2026), anchored on the GCP MLOps levels document

Scope note: consumer is "ml-lab", a local-first framework for gradient-boosted trees run by one researcher plus agents on a laptop and rented pods, no Kubernetes. Research date 2026-10-02. Health numbers (last push, stars, latest PyPI release) were read live from the GitHub and PyPI APIs on that date.

## Q1. What the GCP document actually defines (levels 0/1/2, components, validation steps)

### Takeaway
The GCP document (last updated 2024-08-28, so two years old at research time) defines three maturity levels by what is automated: nothing (0), the training pipeline (1), the build/test/deploy of the pipeline itself (2). It names the feature store as explicitly optional, lists five trigger types, and specifies data validation (schema skew, value skew) and model validation (metrics on a test set, comparison to the current model, per-segment consistency, infrastructure compatibility, then online canary/A/B) as the gates.

### Cited Findings
- Document last updated 2024-08-28 UTC — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Eight ML steps named: data extraction, data analysis, data preparation, model training, model evaluation, model validation ("confirmed to be adequate for deployment, that its predictive performance is better than a certain baseline"), model serving, model monitoring — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Level 0 ("manual process"): "every step is manual, including data analysis, data preparation, model training, and validation"; characteristics: script-driven and interactive, disconnection between ML and operations, infrequent releases, "No CI", "No CD", deployment means only the prediction service, "Lack of active performance monitoring" — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Level 1 ("ML pipeline automation"): goal is "to perform continuous training of the model by automating the ML pipeline"; characteristics: rapid experiment (orchestrated steps), CT of the model in production on live triggers, experimental-operational symmetry ("The pipeline implementation that is used in the development or experiment environment is used in the preproduction and production environment"), modularized components that are "reusable, composable, and potentially shareable" and "ideally be containerized", continuous delivery of models, pipeline deployment ("you deploy a whole training pipeline, which automatically and recurrently runs") — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Level 1 additional components named: data validation and model validation as automated pipeline steps, a feature store ("An optional additional component for level 1 ML pipeline automation is a feature store"), metadata management, pipeline triggers — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Metadata store contents: "Information about each execution of the ML pipeline is recorded in order to help with data and artifacts lineage, reproducibility, and comparisons": pipeline and component versions, execution start/end times, parameter arguments, pointers to artifacts produced by each step, pointer to the previous trained model (for rollback), evaluation metrics — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Five trigger types: on demand, on a schedule, on availability of new training data, on model performance degradation, on significant changes in data distributions (concept drift) — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Level 1 challenge that motivates level 2: "New pipeline implementations aren't frequently deployed; manual testing is typical"; level 2 needed when "Managing many ML pipelines" — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Level 2 ("CI/CD pipeline automation"): six stages: development and experimentation, pipeline CI, pipeline CD, automated triggering, model CD, monitoring; "The data analysis step is still a manual process" — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- CI tests the document lists: unit tests of feature engineering logic, unit tests of model methods, "Testing that your model training converges", "Testing that your model training doesn't produce NaN values", each component produces expected artifacts, integration between components — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- CD checks listed: model compatibility with target infrastructure, calling the prediction service API, prediction service performance (QPS, latency), validating data for retraining or batch prediction — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Data validation: "Required before model training to decide whether you should retrain the model or stop the execution of the pipeline"; detects data schema skews (unexpected features, missing features, unexpected values) and data values skews (significant changes in statistical properties) — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Model validation: evaluation metrics on a test set, "Comparing the evaluation metric values produced by your newly trained model to the current model", performance "consistent on various segments of the data", test for deployment including infrastructure compatibility; then "online model validation, in a canary deployment or an A/B testing setup" — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Model registry appears only in the level 2 diagram narrative ("pushed to the model registry"); the document does not specify its contents — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Monitoring "Collects statistics on the model performance based on live data" and emits triggers for pipeline execution or a new experiment cycle — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Gradual adoption explicitly allowed: "You don't have to immediately move all of your processes from one level to another" — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- The companion whitepaper "Practitioners guide to MLOps" (May 2021, authors Khalid Salama, Jarek Kazmierczak, Donna Schut) lists core capabilities: experimentation, data processing, model training, model evaluation, model serving, online experimentation, model monitoring, ML pipelines, model registry, dataset and feature repository, ML metadata and artifact tracking — [Google whitepaper PDF](https://services.google.com/fh/files/misc/practitioners_guide_to_mlops_whitepaper.pdf)
- The whitepaper states adoption is context dependent: "The decision about whether (or to which degree) to adopt each of these processes and capabilities in your organization depends on your business context ... compared to the cost of purchasing or building capabilities (for example, the cost in engineering hours)" — [Google whitepaper PDF](https://services.google.com/fh/files/misc/practitioners_guide_to_mlops_whitepaper.pdf)

### Inferences
- The document's levels are defined by what is automated, not by which products are installed; every level-1 "component" except the metadata store is described as a pipeline step or a trigger, so a file-based implementation satisfies the definition.
- Both Google documents are enterprise-facing (the whitepaper names its audience as "technology leaders and enterprise architects") and predate the 2025-2026 tooling churn described below; treat the level ladder as a vocabulary, not a 2026 recommendation.

### Gaps
- The GCP document gives no quantitative thresholds for "significant" data drift or "noticeable" degradation; those are left to the implementer.

## Q2. Which parts of level 2 are essential for correctness versus organizational scale

### Takeaway
By the document's own text, the correctness-bearing parts are: a pipeline definition that runs identically in dev and prod (experimental-operational symmetry), a metadata record per run tying code version, parameters and artifact pointers together, and the two validation gates (data, model). The feature store is labeled optional by Google itself; multi-team pipeline CI/CD is motivated only by "managing many ML pipelines"; monitoring-driven triggers presuppose a live serving path. Practitioner guidance in 2026 for solo and 2-3 person teams converges on tracking plus data versioning plus a simple deploy, and explicitly against Kubeflow.

### Cited Findings
- Feature store: "An optional additional component" (Google's own wording) whose stated benefits are discovery and reuse across data scientists and avoiding training-serving skew — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Level 2 is motivated by scale: "Managing many ML pipelines in production requires a CI/CD setup to automate the build, test, and deployment of ML pipelines" — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Metadata requirements (what must be recorded for reproducibility): pipeline/component versions, start/end times, parameters, artifact pointers, previous model pointer, evaluation metrics — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Validation gates are described as the mechanism that decides "whether you should retrain the model or stop the execution of the pipeline" (data) and whether the model is "promoted to production" (model) — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Google whitepaper: adoption of each capability "depends on your business context" and should be weighed against "the cost in engineering hours" — [Google whitepaper PDF](https://services.google.com/fh/files/misc/practitioners_guide_to_mlops_whitepaper.pdf)
- BuildMVPFast (2026-03-29) for a solo or 2-3 person team: "Start with MLflow. It's free, runs locally, and every ML framework integrates with it" and "You don't need collaboration features yet"; Kubeflow only at "20+ ML Engineers with Platform Team" and "only if you already run Kubernetes for other workloads. Standing up Kubernetes specifically for Kubeflow is a decision you'll regret" — [BuildMVPFast](https://www.buildmvpfast.com/blog/mlops-platforms-compared-wandb-mlflow-kubeflow-2026)
- Search-result summaries of 2026 listicles claim Kubeflow is "only worth the complexity if handling 100+ concurrent training jobs or multi-team resource sharing" and recommend "Prefect or ZenML with low setup overhead" for small teams; these are vendor or SEO listicles, lower-quality sources — [Kanerika 2026](https://kanerika.com/blogs/mlops-orchestration/); [TrueFoundry](https://www.truefoundry.com/blog/mlops-tools); [markaicode](https://markaicode.com/vs/mlflow-vs-kubeflow/)
- GitLab's model registry (GA since 17.6, Free tier) links "the model version to the job, giving convenient access to the job's logs, merge request, and pipeline" and exposes an MLflow-compatible client API, showing that a model registry can be a CI feature rather than a separate server — [GitLab docs](https://docs.gitlab.com/user/project/ml/model_registry/)

### Inferences
- For ml-lab: essential = (a) one pipeline definition run by the same code locally and on a pod, (b) a per-run metadata record (code sha, params, data hashes, artifact paths, metrics) in a file or SQLite, (c) a data-schema check and a "beats current model on holdout and per segment" gate before promotion. Organizational scale = feature store, multi-team pipeline CI/CD, canary/A/B online validation, drift-triggered retraining (which requires a serving path and live labels).
- The GCP CI test list ("training converges", "no NaNs", "each component produces expected artifacts") maps directly onto an ordinary pytest suite run in GitHub Actions; no orchestrator is needed to satisfy "pipeline CI".

### Gaps
- No 2025-2026 source found that quantifies, for tabular GBDT specifically, the cost/benefit of a metadata store versus a git-tracked lockfile; the recommendation above is an inference from the definitions.

## Q3. Which orchestrators run local-first with a DAG cache and no daemon, and which target Slurm or plain SSH

### Takeaway
No-daemon, hash-cached DAG runners: DVC (`dvc repro` plus run cache), Snakemake (rerun-on-change plus `--cache`), Nextflow (`-resume`), Apache Hamilton (`.hamilton_cache`), Flyte v2 local (SQLite cache), ZenML local (cache on by default), Prefect 3 (cache records in `~/.prefect/storage`, but persistence is off by default and server requirement is unclear). Slurm from a laptop over SSH is supported by dagster-slurm (JOSS 2026, actively released), metaflow-slurm (SSH + sbatch, last PyPI release 2024-12), and by Snakemake/Nextflow when run on the login node (shared filesystem assumed). Kubeflow, Vertex, Flyte remote, Airflow, Dagster core and ZenML have no Slurm or SSH backend of their own.

### Inferences
- For a laptop plus rented pods with no shared filesystem, the only tools that natively push work over SSH from the laptop are dagster-slurm (requires a Dagster instance and a Slurm cluster) and metaflow-slurm (thin, 2024 release). Snakemake and Nextflow expect to run on the cluster login node. A plain rented pod (RunPod, no Slurm) matches none of the Slurm backends; `ssh pod 'dvc repro'` or `ssh pod 'snakemake ...'` is the realistic pattern, with DVC's remote storage or rsync carrying artifacts back.
- The strongest "DAG cache with no daemon, Python-native" candidates are DVC (file-level hashing, lockfile in git) and Hamilton (function-level hashing, in-process). Snakemake and Nextflow are mature but DSL-based (Snakemake is Python-flavored; Nextflow is Groovy).
- Kubeflow local runners explicitly drop caching and control flow, so KFP cannot serve as a local-first DAG cache.

## Q4. How these tools version a pipeline definition and tie a model artifact to code + data + config

### Takeaway
Two families: lockfile-in-git (DVC `dvc.lock` records dependency, parameter and output hashes per stage; Snakemake and Nextflow hash code, inputs and software environment into the task cache key) versus metadata-database (Vertex ML Metadata, KFP MLMD, ZenML artifact store, Dagster code/data versions, Prefect cache keys, Metaflow datastore snapshots). Only the lockfile family makes the full code+data+config tie reviewable in a plain git diff.

### Cited Findings
- DVC: `dvc.yaml` defines stages with `cmd`, `deps`, `outs`, `params`, `metrics`, `plots`; after a run `dvc.lock` holds "the exact hashes used in the last successful dvc repro" and DVC "compares current state to the lockfile" to detect change — [DVC concepts mirror](https://www.mintlify.com/treeverse/dvc/concepts/pipelines); [DVC repro](https://doc.dvc.org/command-reference/repro)
- Snakemake between-workflow cache hashes "all steps, parameters, software stacks (in terms of conda environments or containers), and raw input required up to a certain job" as a Merkle tree; parameters not declared via `params:` are "not allowed" because they would escape the hash — [Snakemake caching](https://snakemake.readthedocs.io/en/stable/executing/caching.html)
- Nextflow task identity includes container image, Conda/Spack env, inputs, script text and referenced globals — [Nextflow resume](https://docs.seqera.io/nextflow/cache-and-resume)
- Hamilton: code_version hashes the function source ignoring docstrings and comments but "will not version nested function calls", so a changed helper does not invalidate — [Hamilton caching](https://hamilton.apache.org/concepts/caching/)
- Dagster: data version "hashing a code version together with the data versions of any input assets"; `code_version` is a user-supplied string on `@dg.asset`, so it is only as honest as the author — [Dagster versioning](https://dagster.io/docs/guides/build/assets/asset-versioning-and-caching)
- Prefect DEFAULT policy = "the task's inputs, its code definition, as well as the prevailing flow run ID" (so by default no reuse across flow runs unless the policy is changed) — [Prefect caching](https://docs.prefect.io/v3/concepts/caching)
- Vertex: cache key from component interface, input values, output definitions, pipeline name, stored in Vertex ML Metadata — [GCP caching page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/machine-learning/pipelines/configure-caching)
- Metaflow: code snapshots and artifacts persisted to the datastore; `resume` matches by step name, not by content — [Metaflow internals](https://docs.metaflow.org/internals/technical-overview); [Metaflow debugging](https://docs.metaflow.org/metaflow/debugging)
- ZenML cache invalidation considers step code, parameters, input artifact IDs/values, and declared source dependencies, but not filesystem or external API changes — [ZenML caching](https://docs.zenml.io/user-guides/starter-guide/cache-previous-executions)
- GCP's own metadata requirement list (pipeline/component versions, parameters, artifact pointers, previous model pointer, metrics) is the checklist the above should be judged against — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)

### Inferences
- A git-committed `dvc.lock` (or an equivalent hand-rolled JSON lock with sha256 of data, params file, code sha, and model file) satisfies every item on the GCP metadata list except execution timestamps, which a one-line run log covers.
- Caches keyed on user-declared versions (Dagster `code_version`) or on step names (Metaflow `resume`) can silently reuse stale results; content-hash caches (DVC, Snakemake, Nextflow, Hamilton, ZenML) cannot, except for the nested-call blind spot Hamilton documents.

### Gaps
- No source compared cache-key soundness across tools; the ranking above is assembled from each tool's own docs.

### Takeaway
HPC centers document Snakemake, Nextflow, Parsl, Balsam, FireWorks, Maestro and GNU Parallel, not Kubeflow/Airflow/Metaflow. The one bridge from a modern "data orchestrator" to Slurm with peer-reviewed backing is dagster-slurm (JOSS, March 2026, Complexity Science Hub Vienna, targeting EuroHPC Tier-0 systems).

## Q6. What practitioners in 2025-2026 call overkill for small teams

### Takeaway
The consistent 2026 line is: solo and 2-3 person teams use a tracker (MLflow) and data versioning (DVC), deploy with a plain container, and skip Kubeflow and platform adoption entirely; Kubeflow is justified only with an existing Kubernetes platform team and tens of models or 100+ concurrent jobs. Google's own documents support gradual, context-dependent adoption.

### Cited Findings
- BuildMVPFast (2026-03-29): solo/2-3 person team "Start with MLflow. It's free, runs locally"; "You don't need collaboration features yet"; Kubeflow at 20+ engineers with a platform team "only if you already run Kubernetes for other workloads" — [BuildMVPFast](https://www.buildmvpfast.com/blog/mlops-platforms-compared-wandb-mlflow-kubeflow-2026)
- 2026 listicle claims (lower quality, vendor/SEO): "Kubeflow is only worth the complexity if handling 100+ concurrent training jobs or multi-team resource sharing. For under 50 concurrent jobs, Airflow + MLflow is simpler"; "If you're a small team, skip Kubeflow"; "Kubeflow is overkill for simple use cases and has steep operational overhead" — [Kanerika](https://kanerika.com/blogs/mlops-orchestration/); [markaicode](https://markaicode.com/alternatives/kubeflow-alternatives/); [TrueFoundry](https://www.truefoundry.com/blog/mlops-tools)
- Kubeflow's own docs confirm the local path is crippled (no caching, retries, conditionals, resource specs) — [KFP local](https://www.kubeflow.org/docs/components/pipelines/user-guides/core-functions/execute-kfp-pipelines-locally/)
- Metaflow's own docs say the local runtime is "not intended as a production-grade scheduler" and the central metadata service is "not required by Metaflow" — [Metaflow internals](https://docs.metaflow.org/internals/technical-overview)
- Luigi's docs call the no-daemon mode development-only — [Luigi central scheduler](https://luigi.readthedocs.io/en/stable/central_scheduler.html)
- Airflow 3 moved further toward a multi-service architecture (api-server, Task Execution API, Edge Executor), i.e. further from laptop use — [Airflow 3.0 release notes](https://airflow.apache.org/docs/apache-airflow/3.0.0/release_notes.html)
- GCP: "You don't have to immediately move all of your processes from one level to another"; feature store "optional" — [GCP MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)
- Google whitepaper: adopt capabilities to the degree "your business context" justifies against engineering-hour cost — [Google whitepaper PDF](https://services.google.com/fh/files/misc/practitioners_guide_to_mlops_whitepaper.pdf)
- Market churn signals in the period: lakeFS acquired DVC (Nov 2025) and the repo moved to treeverse/dvc; CML's last commit was 2025-06-02; Vertex AI Pipelines docs were relocated under "Gemini Enterprise Agent Platform"; Flyte now ships v1 (flytekit) and v2 (flyte) in parallel — [lakeFS](https://lakefs.io/blog/lakefs-acquires-dvc/); [CML GitHub](https://github.com/iterative/cml); [GCP caching page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/machine-learning/pipelines/configure-caching); [PyPI flyte](https://pypi.org/project/flyte/)

### Inferences
- For ml-lab, the practitioner consensus and the tool docs point the same way: a file-hashed DAG (DVC-style lockfile or Hamilton-style function cache), a git-tracked run record, pytest gates in GitHub Actions, and `ssh pod` for remote runs cover GCP levels 1 and the correctness half of level 2 without any daemon. Adopting Dagster/dagster-slurm becomes worthwhile only if a real Slurm cluster and multiple contributors appear.
- Vendor stewardship changes (DVC to lakeFS, CML idle) argue for depending on file formats (`dvc.lock`-like JSON, git) rather than on a vendor's service.
