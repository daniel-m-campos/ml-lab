# HPC and rented-GPU execution, provenance, and benchmarking rigor (state as of 2026-10-02)

Scope: job submission and remote execution tools, HPC reproducibility tooling, benchmarking rigor on shared hardware, and cost control for rented compute, for a lightweight solo-researcher-plus-agents framework ("forestry"). Repo liveness figures below come from the GitHub REST API queried on 2026-10-02 (`archived`, `pushed_at`, latest release); they are a point-in-time snapshot. Material older than 2024 is marked "(older)".

## Q1. Which tools launch a Python function or script onto a rented pod or Slurm node, stream results back, and tear down, with the least infrastructure?

### Takeaway
For Slurm, Submitit (plus the Hydra launcher for sweeps) is the smallest footprint: a pip package, no daemon, functions pickled and submitted with `sbatch`, results and logs read back through a Job object. For rented pods, SkyPilot and dstack are the two orchestration layers that already speak RunPod, Lambda and Vast.ai and also target Slurm; both need only a pip install plus a local or self-hosted server process. Modal is the least-infrastructure path overall but only on Modal's own compute. slurmrestd, Globus Compute, Ray and Dask-Jobqueue all carry a daemon or a cloud relay.

### Cited Findings
- Submitit is a "Python 3.8+ toolbox for submitting jobs to Slurm"; users create an executor, set parameters such as timeout and partition, submit a function, and receive a Job object with `stdout()` and `stderr()` readers; it supports requeue on preemption, checkpointing of stateful callables, multi-node rank awareness and a `concurrent.futures`-compatible API; the README says it is "not designed as a command-line tool or general task scheduler" and warns against submitting many small tasks. [Submitit README](https://github.com/facebookincubator/submitit)
- Submitit repo liveness: not archived, last push 2026-01-14, 1,641 stars; the GitHub "latest release" object is tag 1.2.0 dated 2021-02-01 (PyPI versions are not tracked by that endpoint, so treat the version as unconfirmed). [GitHub API, queried 2026-10-02](https://api.github.com/repos/facebookincubator/submitit)
- Hydra's Submitit launcher installs with `pip install hydra-submitit-launcher`; `--multirun` sweeps map each parameter combination to a Slurm job through Submitit; config keys include `timeout_min` (default 60), `partition`, `gpus_per_node`, `cpus_per_task`, `mem_gb`, `nodes`, `qos`, `account`, `constraint`, `use_srun`, `python`, `additional_parameters`, and `array_parallelism` (default 256); a `submitit_local` launcher runs the same config without a cluster. - Dask-Jobqueue supports PBS, Slurm, MOAB, SGE, LSF and HTCondor; `SLURMCluster` grows by submitting one scheduler job per worker group; `cluster.adapt(minimum=1, maximum=10)` autoscales; in dynamic mode the Dask scheduler runs where the client runs (usually one compute node) and workers arrive as separate queue submissions; batch-runner mode packs everything into one allocation. [Globus Compute endpoint docs](https://globus-compute.readthedocs.io/en/latest/endpoints/endpoints.html); [Globus Compute tutorial](https://globus-compute.readthedocs.io/en/3.0.0/tutorial.html)

### Inferences
- Minimum-footprint ranking for a solo researcher: Modal (zero infra, but single vendor) < Submitit/Hydra on an existing Slurm login node (pip only) < SkyPilot local mode or dstack server on the laptop (pip plus provider API keys) < Globus Compute (endpoint daemon plus cloud relay) < slurmrestd (needs cluster admin to enable JWT and the daemon) < Ray/Dask clusters (long-lived scheduler processes).
- Submitit's design (pickle the function, write a sbatch script, poll result files on the shared filesystem) is the pattern a pod-oriented framework can imitate over SSH: the "shared filesystem" becomes rsync/scp of a result pickle, and the Job object becomes a handle around a remote PID.
- Determined should be treated as legacy for new work: the OSS repo has been dormant since March 2025 while the commercial HPE product continues.
- dstack's "container-based backend" distinction matters for RunPod and Vast.ai: those providers hand out containers, not VMs, so lifecycle features that assume a VM (idle teardown, see Q4) are absent.

### Gaps
- No primary source was found describing an ad-hoc SSH/rsync "submit a function to a pod" pattern; the closest documented analogues are dstack SSH fleets and Submitit's pickle-and-poll design.
- Submitit's current PyPI version and release cadence were not verified (GitHub releases stop at 1.2.0 while the repo is active).
- Covalent's corporate status (a search summary claimed DataRobot acquired Agnostiq) could not be traced to a primary source and is left unconfirmed.
- Ray Jobs API semantics on Slurm were not covered by the documentation fetched.

## Q2. How do researchers capture hardware identity (CPU model, cache sizes, GPU, driver, container quota) alongside results, and is there any standard schema?

### Takeaway
The only widely used, machine-checked schema is MLPerf's system-description JSON (32 required fields covering host CPU, caches, memory, accelerators, interconnect and software stack). SPEC requires equivalent disclosure in prose. Below that level, practice is ad hoc: hwloc/lstopo for topology, archspec's JSON for microarchitecture naming, and direct reads of cgroup v2 files for container quotas, which neither `os.cpu_count()` nor Python 3.13's `os.process_cpu_count()` account for.

### Cited Findings
- MLPerf's `system_desc_checker` validates 32 mandatory fields: submitter, division, status, system_name, number_of_nodes, host_processors_per_node, host_processor_model_name, host_processor_core_count, host_processor_vcpu_count, host_processor_frequency, host_processor_caches, host_processor_interconnect, host_memory_capacity, host_memory_configuration, host_storage_type, host_storage_capacity, host_networking, host_networking_topology, accelerators_per_node, accelerator_model_name, accelerator_host_interconnect, accelerator_frequency, accelerator_on-chip_memories, accelerator_memory_configuration, accelerator_memory_capacity, accelerator_interconnect, accelerator_interconnect_topology, cooling, hw_notes, framework, other_software_stack, operating_system, sw_notes; for training rulesets 4.1+ `status` must be one of "Available on-premise", "Available cloud", "Research, Development, or Internal (RDI)", "Preview". [mlcommons/logging system_desc_checker.py](https://raw.githubusercontent.com/mlcommons/logging/master/mlperf_logging/system_desc_checker/system_desc_checker.py)
- MLPerf training rules additionally require logging, via mllog, the lowest numerical precision used in linear compute, attention and communication, the tensor/pipeline/context/expert parallelism dimensions, micro-batch size, and the config filename. [MLCommons training_rules.adoc](https://github.com/mlcommons/training_policies/blob/master/training_rules.adoc)
- SPEC CPU 2017 run rules: "A full disclosure of results must include ... a full description of the parts and procedures that are needed to reproduce the result, including but not limited to: hardware, firmware/BIOS, and software", with processor, cache, memory, disk and OS parameters called out. [SPEC CPU2017 run rules](https://www.spec.org/cpu2017/Docs/runrules.html)
- archspec-json ships `cpuid.json` with `cpuid_schema.json` (x86_64 vendor and feature data) and `microarchitectures.json` with `microarchitectures_schema.json`, intended as the base for language APIs that name CPU microarchitectures. [archspec-json README (vendored copy)](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/archspec/json/README.md)
- The Beyer/Löwe/Wendler reliable-benchmarking material tells users to "Type lstopo on your machine (Ubuntu: package hwloc)" to see package, NUMA node, L3/L2/L1 and SMT sibling layout before assigning cores. [Reliable Benchmarking slides, dated 2026-08-10](https://www.sosy-lab.org/research/prs/Latest_ReliableBenchmarking.pdf)
- cgroup v2 `cpu.max` is a two-value file "$MAX $PERIOD" defaulting to "max 100000" (period in microseconds); "the group may consume up to $MAX in each $PERIOD duration"; `cpuset.cpus.effective` is read-only and lists "onlined CPUs that are actually granted to this cgroup by its parent"; `cpu.stat` exposes `nr_throttled` and `throttled_usec` for this cgroup's own bandwidth limit, and `cpu.stat.local` includes throttling inherited from ancestors. [Linux kernel cgroup-v2 docs](https://docs.kernel.org/admin-guide/cgroup-v2.html)
- Python 3.13 added `os.process_cpu_count()` ("number of logical CPU cores usable by the calling thread of the current process") and the `PYTHON_CPU_COUNT` env var / `-X cpu_count` option, described as "useful for users who need to limit CPU resources of a container system without having to modify application code or the container itself"; the What's New text does not mention cgroup quotas. [Python 3.13 What's New](https://docs.python.org/3/whatsnew/3.13.html)
- A practitioner write-up states `os.cpu_count()` and affinity-based counts report the host's CPUs inside a CPU-limited Kubernetes pod while cgroup v2 `cpu.max` enforces the real quota (example "50000 100000" = 0.5 CPU), and recommends reading `cpu.max` and taking ceil(quota/period). [ITNEXT article](https://itnext.io/what-os-cpu-count-gets-wrong-in-a-cpu-limited-kubernetes-pod-ab57756a9153)
- Dask's `dask/system.py` implements CPU-count detection that consults cgroup limits (source visible in a vendored copy). [dask/system.py (vendored copy)](https://dawn2.umd.edu/cwrf-bias-correction-env/lib/python3.1/site-packages/dask/system.py)
- Apache TVM documented a "unified benchmark log format" schema so results could be cross-referenced across frameworks and runs and used for nightly regression (older, TVM v0.9 docs). [TVM benchmark log format](https://tvm.apache.org/docs/v0.9.0/arch/benchmark.html)
- CERN's hep-benchmark-suite aggregates results "into a single JSON document together with hardware metadata such as CPU model, host name, data center name, and kernel version". [hep-benchmark-suite](https://gitlab.cern.ch/hep-benchmarks/hep-benchmark-suite/-/tree/master)
- LLNL's Benchpark material (ICS 2026) argues every performance record needs a JSON sidecar with loaded modules, compiler/MPI versions, GPU drivers and hardware topology. [Benchpark ICS26 slides](https://software.llnl.gov/benchpark/_downloads/a6af6337810986f88c2fb270fe7b6278/ICS26-PArdhapurkar.pdf)

### Inferences
- A forestry hardware fingerprint can be the MLPerf field set, trimmed and extended with three container-aware fields MLPerf lacks: `cpu.max` quota/period (effective vCPUs), `cpuset.cpus.effective` (which physical CPUs), and `cpu.stat` throttling counters captured after the run, since a throttled run is not comparable to an unthrottled one.
- hwloc's XML/JSON export (`lstopo --of xml`) is the natural source for cache sizes and SMT pairing; archspec gives a stable microarchitecture name (e.g. "zen4") that is more useful for grouping results than the raw model string.
- Because `os.process_cpu_count()` is affinity-only, a framework must read cgroup files itself (as Dask does) or it will size thread pools wrongly on RunPod-style containers.

### Gaps
- No cross-vendor "standard" hardware-identity schema beyond MLPerf's submission format was found; MLPerf's schema is oriented to vendor submissions and has no fields for container quotas or cgroup throttling.
- Whether RunPod's pods expose cgroup v1 or v2 files, and whether `cpu.max` reflects the advertised vCPU count, was not verified from a RunPod source.
- No source was found on capturing NVIDIA driver/CUDA version in a schema other than MLPerf's free-text `other_software_stack`.

## Q3. What statistical protocols are recommended for comparing two code versions on noisy shared hardware (interleaving, min vs median, repetitions, bands)?

### Takeaway
Two camps exist and both are current: the "min" camp (Chen and Revels; LLVM's LNT) argues timing noise is additive and positive so the minimum is the least-biased estimator for a deterministic computation; the "distribution" camp (pyperf; SPEC's median-of-3; MLPerf's trimmed mean over 3 to 10 runs) reports central tendency with spread. Everyone agrees on the environmental controls: fixed memory limits, deliberate core assignment respecting SMT, L3 and NUMA, performance governor, turbo off, and either same-host interleaving or isolation. Layout bias (Mytkowicz 2009; Stabilizer 2013, both older) shows that sub-few-percent differences can be artifacts of link order or environment size.

### Cited Findings
- Chen and Revels (2016), "Robust benchmarking in noisy environments", propose a strategy "robust in the presence of timer error, OS jitter and other environmental fluctuations, and ... insensitive to the highly nonideal statistics produced by timing measurements", implemented in Julia's BenchmarkTools and used in Julia's CI. [arXiv 1608.04295](https://arxiv.org/abs/1608.04295) The PDF argues the minimum estimator of true run time "is robust to nonideal statistics and also provides the smallest error". [arXiv PDF](https://arxiv.org/pdf/1608.04295)
- LLVM's LNT performance tracker defaulted to min as its aggregation function (older, 2014 mailing-list thread discussing why). [llvm-dev thread](https://lists.llvm.org/pipermail/llvm-dev/2014-January/069469.html)
- pyperf reports mean and standard deviation, offers median and median absolute deviation as "robust statistics that ignore outliers", flags instability (example: "the maximum (6.02 us) is 39% greater than the mean (4.34 us)" with 9 outliers), links to critiques of min-based reporting (Kevin Modzelewski, Victor Stinner), and recommends `pyperf system tune` to reduce jitter. [pyperf analyze docs](https://pyperf.readthedocs.io/en/latest/analyze.html)
- SPEC CPU 2017: "To run each benchmark three times, in which case the tools use the median time. Or to run each benchmark twice, in which case the tools use the slower of the two runs"; "In order to provide some assurance that results are repeatable, each benchmark is run more than once." No numeric tolerance is given. [SPEC CPU2017 run rules](https://www.spec.org/cpu2017/Docs/runrules.html)
- MLPerf Training: minimum run counts per benchmark are 10 for text-to-image, small LLM pretraining, small LLM MoE, LLM finetuning and recommendation, and 3 for LLM MoE pretraining and LLM post-training; "Each benchmark result is computed by dropping the fastest and slowest runs, then taking the mean of the remaining times"; submitters may run M>N and pick N consecutive runs "closest to the median result" under a deterministic ordering. [MLCommons training_rules.adoc](https://github.com/mlcommons/training_policies/blob/master/training_rules.adoc)
- LLVM's benchmarking guide for Linux: disable ASLR (`echo 0 > /proc/sys/kernel/randomize_va_space`), set `performance` in every `scaling_governor`, shield cores with `cset shield -c N1,N2 -k on`, offline SMT siblings via `/sys/devices/system/cpu/cpuX/online` (siblings listed in `topology/thread_siblings_list`), disable turbo (`echo 1 > /sys/devices/system/cpu/intel_pstate/no_turbo`), run `cset shield --exec -- perf stat -r 10 <cmd>`; the guide claims variation "of less than 0.1%" is achievable. [LLVM Benchmarking.html](https://llvm.org/docs/Benchmarking.html)
- Beyer, Löwe and Wendler, "Reliable Benchmarking: Requirements and Solutions" (STTT 2019; slide version dated 2026-08-10) give a six-item checklist: (1) measure and limit resources accurately (wall and CPU time, include sub-processes, "Always define memory limit for reproducibility", measure peak RSS without sampling), (2) terminate processes reliably (plain `kill` leaves children running), (3) assign cores deliberately (hyper-threading shares execution units; shared caches; "up to 3 different cores inside CPU" with P/E/LP-E), (4) respect NUMA, (5) avoid swapping, (6) isolate runs (communication, filesystem). They show `time` can miss subprocess CPU time and `ulimit -v` applies per process, not per tree. [Reliable Benchmarking slides](https://www.sosy-lab.org/research/prs/Latest_ReliableBenchmarking.pdf); [paper PDF](https://www.sosy-lab.org/research/pub/2019-STTT.Reliable_Benchmarking_Requirements_and_Solutions.pdf)
- BenchExec's user guide adds: without a fixed memory limit "the amount of memory available for benchmarking is non-deterministic"; container mode is required; an NTP daemon is needed because it corrects local clock frequency; BenchExec warns on Turbo Boost and overheating; one parallel run per CPU is "typically" safe but not guaranteed; redirect large outputs to `/dev/null`. [BenchExec benchmarking.md](https://github.com/sosy-lab/benchexec/blob/main/doc/benchmarking.md)
- Mytkowicz, Diwan, Hauswirth and Sweeney (ASPLOS 2009, older): changing UNIX environment size (bytes of environment variables, which shifts stack alignment) or link order of .o files produced measurement bias large enough to flip conclusions; "measurement bias is significant and commonplace in computer system evaluation". [Paper PDF](https://huang.isis.vanderbilt.edu/cs8395/readings/producing-wrong-data.pdf); [USI publication page](https://sape.inf.usi.ch/publications/asplos09)
- Stabilizer (Curtsinger and Berger, ASPLOS 2013, older) re-randomizes code, stack and heap layout at runtime; with layout controlled, "-O3 optimizations over -O2 produce performance improvements indistinguishable from random noise" while -O2 vs -O1 is significant; the tool is unmaintained and works only with LLVM 3.1. [ccurtsinger/stabilizer](https://github.com/ccurtsinger/stabilizer)
- Interleaved A/B in practice: Eigen's CI proposal describes a per-merge-request A/B harness "measuring affected benchmarks interleaved in one CI job". [Eigen work item 3146](https://gitlab.com/libeigen/eigen/-/work_items/3146) Skia's calmbench `ab.py` is an A/B runner that alternates two builds on one host (older). [skia calmbench ab.py](https://skia.googlesource.com/skia/+/chrome/m71/tools/calmbench/ab.py)
- zenbench (Rust) documents interleaving where "each round, all benchmarks run in shuffled order" to spread load drift across arms. [zenbench docs](https://docs.rs/crate/zenbench/latest)
- Ruud van Asseldonk's essay "On benchmarking" (older, 2017) argues that for a deterministic computation the minimum is the right statistic and anything above it is external interference. [ruuda.nl](https://ruuda.nl/2017/on-benchmarking)

### Inferences
- The two camps are reconcilable by purpose: min-over-repeats is the right estimator when comparing two versions of a deterministic kernel on the same host in the same session (the forestry A/B use case), because the comparison cares about intrinsic cost, not expected cost under load; distribution statistics belong when reporting what a user will experience.
- A defensible same-host protocol from these sources: pin both arms to the same cpuset (one SMT sibling per core, one L3 domain, one NUMA node), performance governor and no turbo where the host allows it, fixed memory limit, interleave arms A B A B (not AAAA BBBB) for k rounds, take min per arm, report the ratio with the round-to-round spread as the band; MLPerf-style trimmed mean is the fallback when the workload is nondeterministic.
- Rented pods rarely allow governor or turbo control (containers), so interleaving and ratio-against-co-resident-control become the primary defence; the cgroup throttling counters from Q2 are the check that the quota did not bite one arm more than the other.
- Mytkowicz and Stabilizer imply that a sub-2% A/B difference on a single binary pair is not evidence without either layout randomization or several independent builds.

### Gaps
- No source gives a numeric acceptance band (e.g. "2%") as a standard; SPEC explicitly declines to specify tolerance and MLPerf uses trimmed means rather than bands.
- No 2025-2026 paper specifically on A/B benchmarking inside rented GPU containers was found; the methodology sources are CPU-centric and the GPU-specific sources (MLPerf) are vendor-submission oriented.
- The Chen and Revels full-text numbers (error magnitudes) were not extracted; only the abstract and the min-estimator claim were confirmed.

## Q4. How do SkyPilot, dstack and Determined handle multi-provider GPU stock and preemption, and what is their minimum footprint? (plus provider APIs and cost control)

### Takeaway
SkyPilot's managed jobs re-launch across regions and clouds on preemption and rely on user checkpoints to a mounted bucket; its autostop/autodown runs on the remote cluster with a 5-minute idle default. dstack exposes `spot_policy` (on-demand default, auto, spot) and `idle_duration` (3-day default) but idle teardown does not apply to container backends (RunPod, Vast.ai, Kubernetes), and Vast.ai has no spot support in dstack yet. Determined has no 2025-2026 activity to assess. Provider APIs expose stock directly: RunPod's catalog returns NONE/LOW/MEDIUM/HIGH availability per data center and CUDA version; Vast.ai has a filterable offer search; Lambda rate-limits launches to one per 12 seconds.

### Cited Findings
- SkyPilot managed jobs "can automatically recover from any underlying spot preemptions or hardware failures"; SkyPilot "automatically finds available spot instances across regions and clouds"; on preemption it searches across regions and clouds to re-launch; applications checkpoint to a mounted cloud bucket and reload on restart; the docs cite spot savings of about 70% for GPU VMs. [SkyPilot managed jobs (v0.8.1 docs)](https://docs.skypilot.co/en/v0.8.1/examples/managed-jobs.html); [SkyPilot spot jobs (older v0.5 docs)](https://docs.skypilot.co/en/v0.5.0/examples/spot-jobs.html)
- SkyPilot autostop stops a cluster after idleness (restartable); autodown tears it down; default idle is 5 minutes; set with `autostop: 10m` in YAML, `sky launch -i 10`, or `sky autostop <cluster> -i 10`, and `--down` or `autostop: {idle_minutes: 10, down: true}` converts to autodown; idle means "no in-progress jobs (pending or running) and no active SSH sessions", tunable via `wait_for: jobs_and_ssh | jobs | none`; "The autostop/autodown logic is executed by the remote cluster. Your local machine does not need to stay up". [SkyPilot autostop docs](https://docs.skypilot.ai/en/latest/reference/auto-stop.html)
- SkyPilot footprint: pip install with per-cloud extras; local mode runs as "a standalone application"; a remote API server is optional for multi-user use. [SkyPilot installation docs](https://docs.skypilot.ai/en/latest/getting-started/installation.html)
- dstack `spot_policy`: `on-demand` (default), `auto` (either), `spot` (spot only); run configurations carry their own policy, also defaulting to on-demand. `idle_duration` defaults to 3 days, accepts `0s` or `off`, and never terminates instances at `nodes.min`. [dstack fleets docs](https://dstack.ai/docs/concepts/fleets/)
- dstack: "Idle duration is not applied for container-based backends (Kubernetes, Vast.ai, Runpod)"; auto-created fleets idle 5 minutes by default, adjustable with `termination_idle_time`. [dstack protips](https://dstack.ai/docs/guides/protips/)
- dstack on Vast.ai: "on-demand instances only. Spot instance support coming soon"; Hot Aisle instances may require upfront payment for a minimum reservation period and bill the full period even if stopped early; RunPod and Vast.ai offer Community Cloud options. [dstack backends docs](https://dstack.ai/docs/concepts/backends/)
- RunPod REST v2 `GET /v2/gpu-types?include=AVAILABILITY&product=POD|SERVERLESS|CLUSTER` returns per GPU type: `availability` (NONE, LOW, MEDIUM, HIGH), `dataCenters[]` each with its own `availability`, `cudaVersions[]` with `available` booleans, `price.secure` / `price.community` / `price.serverless` in USD per hour per single GPU, `memory` (GB), `secure`/`community` flags; `maxCount` is a per-machine ceiling, "not current stock"; `product` is required with availability; filters include `countryCodes`, `cudaVersions`, `minCudaVersion`, `count`, `cloudType` (SECURE default, COMMUNITY). [RunPod list GPU types](https://docs.runpod.io/api-reference-v2/catalog/list-gpu-types.md)
- RunPod pod lifecycle: `POST /v2/pods/{id}/action` with `{"action": "terminate"}` permanently deletes the pod and returns 204; permitted actions are published in the pod's `actions` field (RUNNING: stop/restart/terminate; EXITED and ERROR: start/terminate; PROVISIONING and STARTING: stop/terminate). [RunPod pod state transition](https://docs.runpod.io/api-reference-v2/pods/trigger-a-pod-state-transition.md)
- RunPod bills "by the second for compute and storage"; a stopped pod's container disk is free but its volume disk costs $0.20/GB/month; network volumes cost $0.07 or $0.05/GB/month running or stopped; on-demand pods "cannot be displaced by other users". [RunPod pricing](https://docs.runpod.io/pods/pricing)
- Vast.ai CLI: `vastai search offers` "supports all of the filters and sort options that the website GUI uses", e.g. `vastai search offers 'reliability > 0.99 num_gpus>=4' -o 'num_gpus-'` or `'compute_cap >= 800'`; instances are created from an offer id with `vastai create instance <id> --image ... --disk 32 --ssh --direct`. [Vast.ai CLI quickstart](https://vast.ai/docs/cli/quickstart); [Vast.ai hello world](https://docs.vast.ai/cli/hello-world.md)
- Lambda Cloud API: Bearer API key (HTTP Basic also accepted); "Requests to the API are generally limited to one request per second. Requests to the /instance-operations/launch endpoint are limited to one request per 12 seconds, or five requests per minute"; `GET /api/v1/instance-types` lists types with `price_cents_per_hour`; `POST /api/v1/instance-operations/launch` and `/terminate`. [Lambda Cloud API docs](https://docs.lambda.ai/api/cloud)
- AWS gives a Spot interruption notice two minutes before termination; Kubernetes sends SIGTERM and waits `terminationGracePeriodSeconds` (default 30 s); CoreWeave labels nodes `qos.coreweave.cloud/pending-preemption: true` and drains two minutes after the warning. [OneUptime 2026 article on termination handlers](https://oneuptime.com/blog/post/2026-02-09-spot-instance-termination-handler/view); [CoreWeave spot node pools](https://docs.coreweave.com/platform/capacity-plans/spot-node-pools)
- Determined: no repository activity after 2025-03-20 (see Q1), so no 2025-2026 statements about stock or preemption handling exist to cite. [GitHub API](https://api.github.com/repos/determined-ai/determined)

### Inferences
- For a laptop-driven framework, the provider-native stock call (RunPod `include=AVAILABILITY`, Vast `search offers`) is cheaper than adopting SkyPilot or dstack solely for stock discovery; the orchestrators earn their footprint only when cross-provider failover or managed re-launch is wanted.
- Idle teardown on RunPod and Vast.ai must be implemented by the framework itself (a watchdog on the pod or a laptop-side timer calling the terminate endpoint), since dstack explicitly does not apply it there and SkyPilot's autostop runs on the cluster, which on a container backend may not have the same semantics (not verified for RunPod).
- Budget guards fall out of per-second billing plus the `price` fields: price times elapsed seconds is computable client-side before and during a run; the Lambda launch rate limit (1 per 12 s) argues for serial, not parallel, pod creation loops.
- The stopped-pod volume charge ($0.20/GB/month on RunPod) means "stop" is not "free": a teardown protocol should terminate, not stop, unless a warm restart is planned.

### Gaps
- RunPod spot (interruptible) pod semantics, including preemption warning time and signal, were not found in the RunPod docs fetched; search results returned only generic Kubernetes/AWS/CoreWeave material.
- Lambda's `regions_with_capacity_available` field was not confirmed in the fetched excerpt.
- Determined's resource-pool and preemption model was not researched further given the dormant repo.
- Whether SkyPilot autostop functions on RunPod containers specifically was not verified (the docs do not list per-cloud support).

## Q5. What do HPC centers recommend for ML experiment tracking on their systems (offline W&B, MLflow file store, Aim)?

### Takeaway
Evidence found is thin but consistent: NERSC's ML example code recommends Weights & Biases for logging and HPO on Perlmutter; W&B's offline mode (`WANDB_MODE=offline` plus `wandb sync`) and the community `wandb-osh` hook exist precisely for compute nodes without internet; LUMI documents MLflow as a Helm deployment on its LUMI-K Kubernetes side. No center documentation recommending Aim was found.

### Cited Findings
- NERSC's PyTorch DDP example for Perlmutter includes "basic W&B experiment tracking and hyperparameter optimization (HPO)" and NERSC provides "guidelines on using Weights and Biases logging for deep learning applications on NERSC machines", with W&B "recommended as a ML tracking platform for general logging, tracking, and HPO". [ecosyste.ms index of the NERSC example repo](https://awesome.ecosyste.ms/projects/987622)
- NERSC's Machine Learning docs section lists "Distributed training", "Machine Learning Tools" (Overview, Training Launchers, Training Libraries, Hyperparameter Optimization) and TensorBoard, and references Shifter and Podman-hpc containers. [NERSC ML docs](https://docs.nersc.gov/machinelearning/)
- W&B offline: set `WANDB_MODE=offline` to save metrics locally, then `wandb sync [RUN-DIRECTORY]` to upload. [W&B support](https://docs.wandb.ai/support/run_wandb_offline)
- `wandb-osh` ("Wandb Offline Sync Hook") triggers offline syncs "from a compute node without internet" when compute and head nodes share a filesystem, aimed at batch systems. [wandb-osh on PyPI](https://pypi.org/project/wandb-osh)
- LUMI documents MLflow deployment on LUMI-K via Helm from the web UI software catalog or Helm CLI, with custom values overriding chart defaults. [LUMI docs](https://docs.lumi-supercomputer.eu/runjobs/lumi-k/tutorials/mlflow/)
- Ray's Slurm guide points to NERSC-contributed templates for Ray on Slurm. [Ray docs](https://docs.ray.io/en/latest/cluster/vms/user-guides/community/slurm.html)
- Related (lightweight tracking without a server): MLflow's `mlflow-skinny` package is published on PyPI (3.5.x in late 2025), a reduced-dependency client. [mlflow-skinny 3.5.1](https://www.pypi.org/project/mlflow-skinny/3.5.1/)

### Inferences
- The common HPC pattern is "write locally on the shared filesystem during the job, sync from the login node afterwards"; for rented pods the equivalent is "write to the pod's disk, rsync back before teardown", since the pod disappears and (unlike Slurm) there is no persistent shared filesystem unless a network volume is paid for.
- A file-store tracker (MLflow file backend or plain JSONL) matches the HPC posture better than a hosted service because compute nodes and short-lived pods both lack stable outbound connectivity guarantees.

- No ALCF, OLCF or JSC page on experiment tracking was fetched; no primary source found for Aim at any center.
- No center documentation on MLflow file-store usage on Slurm login nodes was found; LUMI's guidance is for its Kubernetes partition.

## Q6. Which environment, container and data-provenance tools fit an HPC-oriented framework in 2026 (Spack, conda-lock, pixi, uv, Apptainer, DataLad, Renku, ReproZip)?

### Takeaway
All eight projects are alive in 2026. Spack's `spack.lock`, pixi's single conda-plus-PyPI lockfile, uv's `uv.lock` and conda-lock's lockfiles are the environment-pinning options, with pixi and uv the "modern" pair recommended by university HPC groups. Apptainer (SIF, unprivileged) remains the HPC container norm. DataLad gained a Slurm-compatible extension in 2025; Renku and ReproZip continue to release.

### Cited Findings
- Spack environments separate `spack.yaml` (abstract specs, preferences, config) from `spack.lock` (fully concretized specs with build hashes); `spack env create myenv spack.lock` reproduces an environment that "when on the same or a compatible machine, is guaranteed to initially have the same concrete specs as the original"; changes to Spack packages are "only picked up when the environment is explicitly re-concretized". [Spack environments docs](https://spack.readthedocs.io/en/latest/environments.html) Spack latest release v1.2.2 on 2026-07-20. [GitHub API](https://api.github.com/repos/spack/spack)
- pixi resolves conda-forge and PyPI packages "together in a single lockfile, using uv internally for PyPI resolution", with project-local environments and a task runner; uv is "the fastest resolver and installer available" with PEP 621 `pyproject.toml` and a cross-platform `uv.lock`, recommended when all dependencies are on PyPI with good wheel support. [pydevtools comparison](https://pydevtools.com/handbook/explanation/uv-vs-pixi-vs-conda-for-scientific-python/)
- UiT (Norway) research-software group published "Using Pixi and uv on a supercomputer" (2025), describing pixi as "a modern take on managing Conda environments" and uv as "a modern take on managing virtual environments". [UiT blog](https://research-software.uit.no/blog/2025-pixi-and-uv/)
- Releases: pixi v0.81.0 (2026-09-15), uv 0.12.22 (2026-10-02), conda-lock v4.0.2 (2026-07-01). [pixi](https://api.github.com/repos/prefix-dev/pixi); [uv](https://api.github.com/repos/astral-sh/uv); [conda-lock](https://api.github.com/repos/conda/conda-lock)
- Apptainer uses the single-file SIF format ("easy to transport and share"), runs unprivileged ("You are the same user inside a container as outside, and cannot gain additional privilege on the host system by default"), keeps a Singularity-compatibility section, and advertises GPU, high-speed network and parallel-filesystem access by default. [Apptainer user guide](https://apptainer.org/docs/user/latest/introduction.html) Latest release v1.5.4 on 2026-09-22. [GitHub API](https://api.github.com/repos/apptainer/apptainer)
- DataLad ("Keep code, data, containers under control with git and git-annex") released 1.6.5 on 2026-09-30. [GitHub API](https://api.github.com/repos/datalad/datalad) A 2025 arXiv paper presents a DataLad extension making it compatible with Slurm batch processing, allowing concurrent jobs on one data repository and avoiding inefficient patterns on parallel filesystems. [arXiv 2505.06558](https://arxiv.org/abs/2505.06558)
- Renku records provenance so that results can be recreated when raw data or preprocessing changes; latest release 2.21.1 on 2026-09-22. [Renku provenance docs](https://renku-docs.readthedocs.io/en/latest/topic-guides/provenance.html); [GitHub API](https://api.github.com/repos/SwissDataScienceCenter/renku)
- ReproZip ("creating reproducible experiments from command-line executions") released 1.3.2 on 2026-01-18 and was last pushed 2026-02-04. [GitHub API](https://api.github.com/repos/VIDA-NYU/reprozip)

### Inferences
- For a C++/CUDA-plus-Python project a two-layer pin is the practical answer: uv or pixi lockfile for Python, Spack lock (or a SIF built from it) for compilers and CUDA; recording the lockfile hash in the result record is cheaper than re-solving to prove identity.
- Apptainer matters only when a Slurm center is in the loop; on RunPod/Vast the unit is already a Docker image, so a framework should treat "image digest" as the environment fingerprint there and "SIF checksum" on clusters.

### Gaps
- No head-to-head 2025-2026 measurement of pixi vs conda-lock vs uv solve times on HPC filesystems was found beyond vendor claims (pixi's "up to 10x" from an arXiv preprint summary, not verified here).
- Spack's `containerize` and binary-cache behaviour for CUDA stacks were not covered by the page fetched.
- ReproZip's suitability for GPU/containerized workloads was not researched.
