## Which metadata schema (MLMD, OpenLineage, MLflow 3, PROV) is small enough for a flat-file or SQLite ledger and still interoperates?

### Takeaway
OpenLineage is the only one of the four that is simultaneously (a) a JSON document schema with no server or ORM baked in, (b) actively released (1.53.0 on 2026-09-01), and (c) already carrying the exact provenance slots a GBDT ledger needs (source-code version that is "not a branch name", dataset version, processing-engine version, environment variables). MLMD is a small SQLite-native relational model but is a C++/Bazel library with a thin release cadence; MLflow 3's LoggedModel is the richest model-centric record but is an application schema, not an interchange format; W3C PROV is stable and tiny but ML tools do not emit it.

### Cited Findings

**ML Metadata (MLMD)**
- MLMD's data model is nine concepts: `ArtifactType`, `Artifact`, `ExecutionType`, `Execution`, `Event` ("a record of the relationship between artifacts and executions"), `ContextType`, `Context` (e.g. "project name, changelist commit id, experiment annotations"), `Attribution` (artifact to context) and `Association` (execution to context) — [TFX MLMD guide](https://www.tensorflow.org/tfx/guide/mlmd)
- MLMD storage backends are "SQLite reads and writes files from disk", MySQL and PostgreSQL, plus an optional gRPC server mode — [TFX MLMD guide](https://www.tensorflow.org/tfx/guide/mlmd)
- The repository README still states "ML Metadata may be backwards incompatible before version 1.0" and Windows is deprecated past MLMD 1.14.0 — [google/ml-metadata](https://github.com/google/ml-metadata)
- Health: 687 stars, not archived, last push 2026-08-14, latest release v1.21.0 on 2026-06-09; PyPI uploads were 1.15.0 (2024-04-23), 1.16.0 (2024-10-01), 1.17.0 (2025-04-07), 1.17.1 (2026-02-05), 1.21.0 (2026-06-09), i.e. roughly one or two releases per year tied to the TFX cadence — [GitHub API, google/ml-metadata](https://github.com/google/ml-metadata); [PyPI ml-metadata](https://pypi.org/project/ml-metadata/)

### Inferences
- A flat-file ledger can be a directory of OpenLineage `RunEvent` JSON documents (one per training run) plus a SQLite index; the facet mechanism lets forestry add a `forestry_model` custom facet (bytes hash, library version, params) without leaving the spec, and any Marquez or Airflow consumer will still parse the core event. The spec's own rule that `_schemaURL` be pinned to a git sha matches the project's "tie every result to a code sha" requirement.
- MLMD's model (Artifact/Execution/Context + Event) is the right relational shape for SQLite and is what Vertex and Kubeflow still use, but adopting the library drags in Bazel-built C++ wheels and a cadence of one or two releases a year; copying the nine-table shape into forestry's own SQLite schema is cheaper than depending on it.
- MLflow 3's `Metric(model_id, dataset_name, dataset_digest)` triple is the most complete published answer to "which model, scored on which data", but MLflow's digest is an 8-hex-char md5 over the first 10,000 rows, which is a fingerprint for UI dedup, not an integrity hash; forestry should keep MLflow-compatible field names (`digest`, `source`, `model_id`) while storing a full content hash.
- PROV is the only W3C-grade vocabulary; mapping forestry records to PROV-O (Entity=model/data, Activity=training run, Agent=host/user) is a one-page exporter, not a storage format. RO-Crate 1.2 is the practical JSON-LD container if a PROV-ish export is ever wanted.

### Gaps
- No OpenLineage facet for a trained model or a model registry was found; whether an ML facet proposal exists on the OpenLineage GitHub proposals board was not checked.
- MLMD's exact SQLite schema version and the release notes for 1.21.0 were not fetched (the GitHub README page returned only summary content).
- PROV-JSON's status beyond "Member Submission" was not verified.

## How do teams version tabular datasets of 1-100 GB without a server (DVC remotes, lakeFS, content hashes in a manifest, Xet)?

### Takeaway
Serverless options in 2026 are DVC (md5 content-addressed cache plus any local, SSH, or object-store remote), git-annex/DataLad (SHA256E keys, `datalad run` records), and Oxen (merkle tree, xxh3/sha2, optional self-hosted server). Xet is the best deduplication technology measured, but its content-addressed store is Hugging Face's hosted CAS, not something you can run locally. lakeFS and Pachyderm are server products; lakeFS now also owns DVC. For hashing tabular data, Parquet bytes are not reproducible across writers, so a manifest should hash either the stored bytes once (physical hash) or a canonical Arrow encoding (logical hash).

### Cited Findings

**DVC**
- "DVC calculates the file hash, a 32 characters long string (usually MD5)"; the cache path is `.dvc/cache/files/md5/xx/yyy` (first two hex chars as directory); directories get a `.dir` entry that "contains the mapping of files inside (as a JSON array)" of `{"md5": ..., "relpath": ...}`; identical contents are stored once — [DVC internal files](https://doc.dvc.org/user-guide/project-structure/internal-files)
- `.dvc` output fields: `path` (required), `hash` ("Hash algorithm for the file or directory being tracked with DVC (only `md5` is currently supported)"), `md5`/`etag`/`checksum`, `version_id` ("Version ID native to the cloud provider"), `size`, `nfiles`, `isexec`, `cache`, `remote`, `persist`, `push` — [DVC .dvc files](https://doc.dvc.org/user-guide/project-structure/dvc-files)
- Remote types: Amazon S3 and S3-compatible (MinIO), Azure Blob, Google Cloud Storage, Google Drive, Aliyun OSS, SSH/SFTP, HDFS/WebHDFS, HTTP, WebDAV, and "local remotes" (system directories, mounted drives, NAS); local and SSH remotes need no dedicated server — [DVC remote storage](https://doc.dvc.org/user-guide/data-management/remote-storage)
- lakeFS announced on 2025-11-18 that it acquired the DVC open source project from Iterative.ai; "DVC ... will continue as an independent open source tool focused on data scientists working with smaller datasets, while lakeFS will continue to advance enterprise-grade data version control infrastructure" — [lakeFS acquires DVC](https://lakefs.io/blog/lakefs-acquires-dvc/); [DVC blog: your questions answered](https://dvc.org/blog/dvc-joins-lakefs-your-questions-answered/)
- Health: iterative/dvc 15,901 stars, Apache-2.0, last push 2026-09-28, latest release 3.67.1 on 2026-03-31 (six months without a release at the time of reading) — [GitHub API, iterative/dvc](https://github.com/iterative/dvc); [PyPI dvc](https://pypi.org/project/dvc/)
- Oxen's own benchmark (vendor blog, 2024-12-26) on ImageNet: DVC 3 hours local, about 5 hours to S3; Git LFS 20 hours; Oxen "fastest" without a stated number — [Oxen blog](https://ghost.oxen.ai/the-best-ai-data-version-control-tools/)

**lakeFS**
- lakeFS is "a scalable, open-source data versioning tool that uses Git-like semantics, supporting petabytes of data in any format", with the disadvantage of "having to handle file storage yourself" (secondary source) — [ZenML DVC alternatives](https://www.zenml.io/blog/dvc-alternatives)
- Health: treeverse/lakeFS 5,551 stars, license reported as NOASSERTION by GitHub, last push 2026-10-01, latest release v1.88.0 on 2026-10-01 — [GitHub API, treeverse/lakeFS](https://github.com/treeverse/lakeFS)

**git-annex and DataLad**
- git-annex default key backend is SHA256E, which "combines a 256 bit SHA-2 hash of the file's content with the file's extension"; other backends: SHA256, SHA512/SHA512E ("for the very paranoid"), BLAKE2 variants, MD5/MD5E, WORM ("Write Once, Read Many", keyed on filename, size, mtime), URL, VURL ("the content can be verified with a cryptographically secure checksum"); "the key includes the backend that is used for that key" — [git-annex backends](https://git-annex.branchable.com/backends/)
- `datalad run` "generates a run record in the commit, which can be used by datalad to re-execute a command with `datalad rerun SHASUM`" — [DataLad handbook](https://handbook.datalad.org/en/0.15/basics/101-113-summary.html)
- DataLad 1.6.0 (2026-06-09): "datalad run now wraps command-created commits as merge commits, preserving linear first-parent history while keeping the full provenance record"; latest release 1.6.5 on 2026-09-30 — [DataLad changelog](https://docs.datalad.org/changelog.html)
- Health: datalad/datalad 664 stars, last push 2026-10-02 — [GitHub API, datalad/datalad](https://github.com/datalad/datalad)

**Pachyderm**
- HPE announced the Pachyderm acquisition in January 2023; "the product remains available along with the source code" — [Pachyderm blog](https://pachyderm.com/blog/hewlett-packard-enterprise-acquires-pachyderm-to-expand-ai-at-scale-capabilities-with-reproducible-ai)

**Oxen**
- Oxen is Rust, Apache-2.0, 1,193 stars, latest release v0.61.0 on 2026-10-02; it "caches this information in the merkle tree"; `Cargo.toml` depends on `xxhash-rust` (feature `xxh3`) and `sha2`; a self-hosted `oxen-server` runs on Linux and macOS (not Windows); an `experiments/block-level-dedup` folder exists — [Oxen-AI/Oxen](https://github.com/Oxen-AI/Oxen)

**Xet (Hugging Face)**
- Xet uses content-defined chunking at "~64KB"; "Each chunk is identified by a rolling hash that determines chunk boundaries based on the actual file contents"; new chunks "are grouped into 64 MB blocks and uploaded. Each block is stored once in a content-addressed store (CAS), keyed by its hash"; dedup is checked against the session, a local cache, then "a subset of chunks are checked against all of Xet storage via a global deduplication query" — [Hub docs: deduplication](https://huggingface.co/docs/hub/xet/deduplication)
- A Xet pointer keeps the Git LFS fields (SHA256 of content, size) "with the addition of a `Xet backed hash` field"; "Unlike Git LFS, which deduplicates at the file level, Xet-enabled repositories deduplicate at the level of bytes" — [Hub docs: Xet overview](https://huggingface.co/docs/hub/xet/overview)
- On download, `hf_xet` "will query the Xet content-addressable service (CAS) with the LFS SHA256 hash for this file to receive the reconstruction metadata (ranges within xorbs)"; `hf_xet` ships with `huggingface_hub` since 0.32.0; `hf_transfer` is deprecated — [huggingface_hub download guide](https://huggingface.co/docs/huggingface_hub/en/guides/download)
- "The migration was massive, starting with 20 petabytes across over 500,000 repositories" and "All 77PB+ over 6,000,000 repositories have been migrated to the Xet backend"; huggingface_hub v1.0 released 2025-10-27 — [HF blog: huggingface_hub v1.0](https://huggingface.co/blog/huggingface-hub-v1)
- xet-core describes itself as handling "concurrent communication to HF Hub Xet backend services (CAS)" and `xet-client` as the "HTTP client for communicating with Hugging Face Xet storage servers"; 605 stars, v1.6.0 on 2026-08-03; `hf_xet` 1.6.0 on PyPI 2026-08-03 — [huggingface/xet-core](https://github.com/huggingface/xet-core); [PyPI hf-xet](https://pypi.org/project/hf-xet/)
- Hub revisions can be pinned to a commit: "When using the commit hash, it must be the full-length hash"; the local cache stores files under `snapshots/<commit sha>/` — [huggingface_hub download guide](https://huggingface.co/docs/huggingface_hub/en/guides/download)

**Hashing Parquet/Arrow data**
- Parquet is "non-reproducible (non-deterministic)": "heuristics around encodings (e.g. RLE vs bitpack), heuristics around batch sizes, different settings for statistics, etc." make logically identical data differ at the byte level; the RFC distinguishes a physical hash (digest of the file, for content-addressable storage) from a logical hash (digest over records, for integrity and equivalence) and implements the logical hash over the Arrow in-memory layout with SHA3-256, multihash codec `arrow0-sha3-256` — [kamu ODF RFC-002](https://docs.kamu.dev/odf/rfcs/002-logical-data-hashes)
- The `arrow-digest` crate implementing that scheme has 13 stars and no tagged release — [kamu-data/arrow-digest](https://github.com/kamu-data/arrow-digest)
- MLflow's own dataset digest is a sample-row md5 truncated to 8 hex characters (see question 1) — [mlflow/data/digest_utils.py](https://github.com/mlflow/mlflow/blob/master/mlflow/data/digest_utils.py)
- Croissant records per-file `sha256`/`md5` on `FileObject` — [Croissant spec](https://docs.mlcommons.org/croissant/docs/croissant-spec.html)

### Inferences
- For 1-100 GB tabular data with no server, the working pattern is a manifest of `{path, size, sha256 (or md5 for DVC compatibility), nrows, schema hash}` committed to git, with bytes in a content-addressed directory or object store. DVC already does this with md5 and `.dir` JSON manifests; adopting its field names (`md5`, `size`, `nfiles`) keeps `dvc` as a drop-in reader.
- Because Parquet is not byte-reproducible, "data version" should be the hash of the bytes as stored (never re-serialized), with an optional Arrow logical hash when equivalence across writers matters. Re-writing Parquet in a pipeline step and expecting the hash to hold is the failure mode to design against.
- Xet-style CDC dedup is only worth building locally if datasets are edited in place (appended rows, changed columns); for snapshot-style tabular data, whole-file hashing with DVC-style dedup of identical files captures most of the benefit without a CAS service.
- DVC's cadence (one release in six months, new owner) and Pachyderm's silence (20 months) are both signals to depend on the file formats rather than the tools.

Whether lakeFS has a credible single-binary local mode for a laptop is therefore unverified here.
- No HPE statement on Pachyderm end-of-life was found; the inactivity signal is from GitHub only.

- No independent (non-vendor) 2025-2026 benchmark comparing DVC, lakeFS, Oxen and Xet on tabular data was found; the only numbers are Oxen's own.

## What is the minimal registry record for a GBDT model (bytes hash, library version, params, training data hash, metrics, host), and does any standard define it?

### Takeaway
No standard defines a GBDT registry record. The closest are: MLflow's `MLmodel` plus `LoggedModel`/`Metric(model_id, dataset_digest)`; scikit-learn's documented "additional metadata" list; CycloneDX `modelCard`; CNCF ModelPack's `descriptor` (with a `revision` field for source control) plus OCI content digests; and the Hugging Face model-card YAML (`model-index`, `datasets`, `base_model`). The model bytes themselves have four portable homes: the library's native format (XGBoost UBJSON/JSON, LightGBM text, CatBoost cbm), ONNX `ai.onnx.ml.TreeEnsemble`, PMML 4.4.1, and Treelite; skops is the safe-pickle option for sklearn-API wrappers.

### Cited Findings

**Fields the existing standards agree on**
- scikit-learn: "In order to rebuild a similar model with future versions of scikit-learn, additional metadata should be saved along the pickled model: The training data, e.g. a reference to an immutable snapshot; The Python source code used to generate the model; The versions of scikit-learn and its dependencies; The cross validation score obtained on the training data"; also "there are no supported ways to load a model trained with a different version of scikit-learn" and `InconsistentVersionWarning` exposes `original_sklearn_version` — [scikit-learn model persistence](https://scikit-learn.org/stable/model_persistence.html)
- MLflow `MLmodel`: `flavors`, `time_created`, `run_id`, `signature`, `input_example`, `mlflow_version`, with `conda.yaml`, `python_env.yaml`, `requirements.txt` beside it — [MLflow model docs](https://mlflow.org/docs/latest/ml/model/)
- MLflow `LoggedModel` adds `model_id`, `model_type`, `source_run_id`, `status`, `params`, `tags`, `metrics`; each `Metric` carries `dataset_name`, `dataset_digest`, `model_id` — [logged_model.py](https://github.com/mlflow/mlflow/blob/master/mlflow/entities/logged_model.py); [metric.py](https://github.com/mlflow/mlflow/blob/master/mlflow/entities/metric.py)

### Inferences
- A defensible minimal record, assembled from field names the standards already use: `model_id` (MLflow), `format` + `bytes_sha256` + `size` (OCI descriptor), `library` + `library_version` (`MLmodel` flavor), `params` (MLflow `LoggedModel.params`, XGBoost `save_config`), `code.version` = git sha (OpenLineage `SourceCodeLocationJobFacet.version`, ModelPack `descriptor.revision`), `dataset.digest` + `dataset.source` (MLflow `Dataset`), `metrics[].{key,value,dataset_digest}` (MLflow `Metric`), `env` (`requirements.txt`/lockfile hash, container digest), `host` (Sacred-style `cpu`, `gpu`, `os`, `hostname`), `created_at` (RFC 3339 per ModelPack). Nothing standard carries the host block; see the environment section.
- Storing the native library format (UBJSON for XGBoost, text for LightGBM, cbm for CatBoost, bonsai's msgpack) as the canonical bytes and hashing those is the only option with a backward-compatibility promise from the producer (XGBoost states one explicitly). ONNX `TreeEnsemble` v5 is the one cross-library interchange that can represent all four, but converters (onnxmltools, skl2onnx) release twice a year and lag library majors.
- PMML is alive as a vendor interchange (JPMML releases monthly) but its 2019 spec date, AGPL converter and lack of multiclass support in CatBoost's exporter make it a secondary export, not the registry's canonical bytes.
- safetensors is irrelevant to tree models beyond its header idea: an 8-byte length prefix plus a JSON header with a string-to-string `__metadata__` map is a reasonable template for a self-describing model file.

### Gaps
- Whether ModelPack has a tagged spec release was not determinable: the GitHub API reports no releases for `modelpack/model-spec` (232 stars).
- LightGBM's model text format version field and its stability promise were not fetched.
- The ORAS CLI documentation (`--artifact-type`, per-layer media types) was only seen through secondary pages and is not cited as primary.
- No published count of GBDT models stored in OCI registries or on the Hub by library was found.

## How are cross-platform byte-identical model gates done in practice (XGBoost/LightGBM/CatBoost determinism docs, CI hash checks)?

### Takeaway
No GBDT library promises byte-identical models across machines; all three limit the promise to "same machine, same build" with caveats (LightGBM says results differ across "different LightGBM versions, binaries compiled by different compilers, or in different systems"; XGBoost's GPU path became deterministic for single-GPU regression/classification in 1.1.0 but not ranking or multi-GPU; CatBoost states GPU training is non-deterministic). Projects that gate on bytes do so as reproducible-builds-style golden hashes: fixed data, fixed seed, fixed thread count, one hash per (platform, build), compared in CI; bonsai's `scripts/model_hash.py` is a worked example.

### Cited Findings

**Library statements**
- LightGBM `deterministic` (default false, CPU only): "setting this to `true` should ensure the stable results when using the same data and the same parameters (and different `num_threads`)"; "when you use different seeds, different LightGBM versions, binaries compiled by different compilers, or in different systems, the results are expected to be different"; "to avoid potential instability due to numerical issues, please set `force_col_wise=true` or `force_row_wise=true` when setting `deterministic=true`"; "setting this to `true` may slow down the training"; `seed` "has lower priority in comparison with other seeds" — [LightGBM Parameters](https://lightgbm.readthedocs.io/en/latest/Parameters.html)
- LightGBM FAQ: "When using LightGBM GPU, I cannot reproduce results over several runs. This is normal and expected behaviour, but you may try to use `gpu_use_dp = true` for reproducibility"; "LightGBM bagging is multithreaded, so its output depends on the number of threads used" was fixed by PR #2804 so "bagging result doesn't depend on the number of threads" — [LightGBM FAQ](https://lightgbm.readthedocs.io/en/latest/FAQ.html)
- XGBoost FAQ on slightly different results: "This could happen, due to non-determinism in floating point summation order and multi-threading. Also, data partitioning changes by distributed framework can be an issue as well" — [XGBoost FAQ](https://xgboost.readthedocs.io/en/stable/faq.html)
- XGBoost 1.1.0 (2020-05-17): "GPU algorithm for regression and classification tasks is now deterministic"; "Currently only single-GPU training is deterministic. Distributed training with multiple GPUs is not yet deterministic"; "CUDA 10.0 is necessary to make the GPU algorithm deterministic (#5361)"; "GPU ranking objective is currently not deterministic (#5561)" — [XGBoost v1.1.0 release](https://github.com/dmlc/xgboost/releases/tag/v1.1.0)
- Issue #5632 "XGBoost 1.1.0 SNAPSHOT gpu_hist still numerically unstable" (opened 2020-05-05, closed) shows a user re-testing the determinism claim with a nightly wheel and a fixed-seed script — [dmlc/xgboost#5632](https://github.com/dmlc/xgboost/issues/5632)
- XGBoost 2.1.0: "Sort workers by task ID. This helps the PySpark interface obtain deterministic results. (#10220)" — [XGBoost v2.1.0 changes](https://github.com/dmlc/xgboost/blob/master/doc/changes/v2.1.0.rst)
- XGBoost linear updater docs: `shotgun` "Uses 'hogwild' parallelism and therefore produces a nondeterministic solution on each run"; `coord_descent` is "multithreaded but still produces a deterministic solution"; `greedy` feature selector "is fully deterministic" — [XGBoost parameter.rst](https://github.com/dmlc/xgboost/blob/master/doc/parameter.rst)
- A `deterministic_histogram` flag ("XGBoost builds histogram on GPU deterministically", `gpu_hist` only) appears in the SageMaker XGBoost hyperparameter reference — [AWS SageMaker XGBoost hyperparameters](https://docs.aws.amazon.com/sagemaker/latest/dg/xgboost_hyperparameters.html)
- CatBoost FAQ: "Training on GPU is non-deterministic, because the order of floating point summations is non-deterministic in this implementation" — [CatBoost FAQ](https://catboost.ai/docs/en/concepts/faq); `random_seed` is supported on CPU and GPU, default 0 — [CatBoost common parameters](https://catboost.ai/docs/en/references/training-parameters/common)
- PyTorch: "Completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms"; "Results may not be reproducible between CPU and GPU executions, even when using identical seeds"; `torch.backends.cudnn.benchmark = False` "causes cuDNN to deterministically select an algorithm"; `torch.use_deterministic_algorithms()` is broader than `cudnn.deterministic` — [PyTorch reproducibility notes](https://docs.pytorch.org/docs/stable/notes/randomness.html)
- mlf-core (arXiv 2104.07651, 2021, revised 2022-06-16): "major machine learning libraries default to the usage of non-deterministic algorithms based on atomic operations"; it demonstrates deterministic project templates for TensorFlow, PyTorch and an XGBoost cancer classifier — [mlf-core](https://arxiv.org/abs/2104.07651)

**Cross-hardware bitwise work (2025-2026)**
- Thinking Machines (2025-09): LLM inference nondeterminism "leaks in because the server groups requests into different batches over time, and several kernels are not batch invariant"; with batch-invariant RMSNorm, matmul and attention kernels on vLLM, 1000 identical runs went from 80 unique completions to 1, at a cost of 26 s to 42 s on one task — [Defeating nondeterminism in LLM inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference)
- OPEN-1B (arXiv 2609.17380, submitted 2026-09-15) defines "fully auditable" as "every operation on every data sample during training is independently reproducible on heterogeneous commodity hardware with bitwise certainty", achieved by imposing "definite order on sources of training nondeterminism: GPU kernel reductions, data batch ordering across data-parallel clusters, and inter/intra-node collective communication", with a "collective verification scheme" where independent auditors each replay individual steps — [OPEN-1B](https://arxiv.org/abs/2609.17380)
- Reproducible Builds definition: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts", verified by comparing cryptographic hashes — [reproducible-builds.org](https://reproducible-builds.org/docs/definition/)

**CI gate patterns**
- LightGBM issue #4407 "[ci] regression tests: model files" (2021-06-25, closed) specifies a CI job testing "Model files produced in LightGBM version `(N).x.x` should be readable and usable in all versions in the same major version series", covering models saved via `LGBM_BoosterSaveModelToString()` — [microsoft/LightGBM#4407](https://github.com/microsoft/LightGBM/issues/4407)
- A CERN DAQ project's hash-based regression testing stores golden hashes named `{file_prefix}_{number of bytes hashed}_{version commit number}` and fails when the hash of a fresh output differs for the same byte prefix — [CERN scdaq MR 83](https://gitlab.cern.ch/scouting-demonstrator/scdaq/-/merge_requests/83)
- bonsai's wire-identity gate trains "a fixed 500k x 100 depthwise model and prints a short sha256 of the saved msgpack. Any refactor that claims to preserve CPU behavior must leave this hash unchanged; capture the baseline BEFORE touching anything"; parameters pin `parallel.n_threads = 8`, `booster.n_iters = 20`, `tree.max_depth = 8`, `bin_mapper.max_bin = 255`; the data seed is `SeedSequence([42, 500_000, 100])`; the hash is `sha256(...)[:16]`; "the device contract is identity run to run on one device and build, so the gate there is three runs printing one hash" — [bonsai scripts/model_hash.py](/Users/danielmcampos/work/mpcs/bonsai/scripts/model_hash.py)
- Sacred records, for each run, source files as "(filename, md5sum)" tuples, the repository "url ..., the current commit hash and whether the repository is dirty", and dependencies as "package==version" — [Sacred collected information](https://sacred.readthedocs.io/en/stable/collected_information.html)

### Inferences
- "Byte-identical across platforms" is not something any GBDT vendor claims; the achievable contract is byte-identical per (OS, CPU ISA or GPU arch, compiler, library build), which is exactly the reproducible-builds framing. A registry therefore needs the hash keyed by a platform fingerprint, and a gate that compares a fresh hash against the golden hash for the same key.
- The practical recipe shared by bonsai, mlf-core and the CERN example is: fixed synthetic or pinned dataset (hash recorded), fixed seed, fixed thread count, deterministic flags on (`deterministic=true` + `force_row_wise` for LightGBM; single-GPU hist for XGBoost; CPU for CatBoost), hash the serialized model bytes, store the golden hash per platform in the repo, fail CI on mismatch, and re-pin only in a commit that names why.
- Thread-count independence is a separate, stronger property that LightGBM claims (with `deterministic`) and XGBoost does not document for CPU `hist`; a gate should pin threads rather than assume invariance.
- GPU gates should be "N runs, one hash" on a single device (bonsai's rule) and should never compare against a CPU hash.

### Gaps
- NVIDIA's cuDNN reproducibility page (bit-wise reproducibility not ensured across versions and architectures) returned 404 at the URL tried; the statement is widely quoted but not verified here against a primary page.
- XGBoost documentation does not state whether CPU `hist` results are independent of `nthread`; no primary source either way was found.
- LightGBM's test suite was searched for `deterministic` tests via GitHub code search, which returned no results (likely a search-scope limitation), so the existence of an in-repo determinism test is unconfirmed.
- No public CI from XGBoost, LightGBM or CatBoost that asserts a byte-identical golden model hash was found; the LightGBM issue covers load compatibility, not byte identity.

## Environment capture: lockfiles (uv, pixi, conda-lock), container digests, hardware fingerprints

### Takeaway
Lockfiles are solved for Python (uv.lock universal, pixi.lock per-platform with sha256+md5, conda-lock multi-solve), container identity is the OCI sha256 digest, but there is no standard hardware fingerprint; the de facto practice (Sacred, W&B, mlf-core) is to record CPU model, GPU model and driver/CUDA version, OS and hostname as free-form fields, and OpenLineage's `ProcessingEngineRunFacet` + `EnvironmentVariablesRunFacet` are the only schema slots that come close.

### Cited Findings
- uv: "uv.lock is a universal or cross-platform lockfile that captures the packages that would be installed across all possible Python markers such as operating system, architecture, and Python version"; "The uv.lock format is specific to uv and not usable by other tools"; "some of uv's functionality cannot be expressed in the pylock.toml format" (PEP 751) so uv keeps its own format; uv 0.12.22 (2026-10-02), 90,379 stars — [uv project layout](https://docs.astral.sh/uv/concepts/projects/layout/); [astral-sh/uv](https://github.com/astral-sh/uv)
- pixi: the lock file is resolved "for all environments and platforms listed in the manifest"; package entries carry `sha256` and `md5`; the file carries `version: 6`; `--frozen` installs "as defined in the lock file, doesn't update pixi.lock if it isn't up-to-date with manifest file", `--locked` installs "only ... if the pixi.lock is up-to-date with the manifest file"; pixi v0.81.0 (2026-09-15), 7,818 stars, BSD-3 — [pixi lock file docs](https://pixi.prefix.dev/latest/workspace/lock_file/); [prefix-dev/pixi](https://github.com/prefix-dev/pixi)
- conda-lock produces a "unified lockfile format" by performing "multiple solves for conda/mamba targeting a set of platforms", with "integrated pip support" and "solveless conda installation"; inputs include environment.yml, meta.yaml and pyproject.toml; v4.0.2 (2026-07-01), 565 stars — [conda-lock docs](https://conda.github.io/conda-lock/); [conda/conda-lock](https://github.com/conda/conda-lock)
- "conda's environment.yml is a specification, not a lock"; pixi "resolves conda-forge packages and PyPI packages together in a single lockfile, using uv internally for PyPI resolution" and can pin "CUDA toolkits, GDAL, HDF5, compilers" (secondary, practitioner handbook) — [pydevtools: uv vs pixi vs conda](https://pydevtools.com/handbook/explanation/uv-vs-pixi-vs-conda-for-scientific-python/)
- OCI content digest `sha256:<hex>` is mandatory to verify, with `mediaType` and `size` required on every descriptor — [OCI descriptor](https://github.com/opencontainers/image-spec/blob/main/descriptor.md)
- Sacred host info fields: `cpu` ("The CPU model"), `hostname`, `os`, `python_version`, `gpu` ("Information about NVidia GPUs (if any)"), `ENV` (captured environment variables, empty by default, extendable via `sacred.SETTINGS.HOST_INFO.CAPTURED_ENV`) — [Sacred collected information](https://sacred.readthedocs.io/en/stable/collected_information.html)
- W&B writes a `wandb-metadata.json` per run and logs system metrics (CPU, GPU utilization and memory) every 15 seconds (search-level evidence) — [W&B system metrics](https://docs.wandb.ai/ref/system-metrics)
- OpenLineage `ProcessingEngineRunFacet` records `name`, `version`, `openlineageAdapterVersion`; `EnvironmentVariablesRunFacet` records `{name, value}` pairs — [OpenLineage spec/facets](https://github.com/OpenLineage/OpenLineage/tree/main/spec/facets)
- MLflow stores `conda.yaml`, `python_env.yaml` and `requirements.txt` beside every model — [MLflow model docs](https://mlflow.org/docs/latest/ml/model/)
- scikit-learn: "Persisted models are often deployed in production using containers like Docker, in order to freeze the environment and dependencies" — [scikit-learn model persistence](https://scikit-learn.org/stable/model_persistence.html)

### Inferences
- The environment half of a forestry record can be three hashes: sha256 of the lockfile actually used (`uv.lock`, `pixi.lock` or `conda-lock.yml`), the OCI image digest if containerized, and sha256 of a canonical host JSON (`cpu_model`, `cpu_flags` subset, `gpu_model`, `driver`, `cuda_runtime`, `os`, `kernel`, `compiler`, `blas`). The third is what no standard defines and what the determinism gate must key on.
- pixi is the only lockfile among the three that pins CUDA toolkits and compilers in the same file as Python packages, which matters for GBDT libraries whose numerics depend on the compiler.

### Gaps
- No standard or widely adopted "hardware fingerprint" schema was found; every tool uses ad hoc fields.
- The `--locked`/`--frozen` flags and hash coverage of `uv.lock` were not confirmed on the uv page fetched (only the universal-lock and uv-specific-format statements were).

### Inferences
- For a local-first framework the safest external dependencies by health are OpenLineage (schema only, no server), MLflow's `MLmodel`/`LoggedModel` field names (compatibility, not the server), OCI digests, and pixi/uv lockfiles. MLMD, Marquez and PMML are stable but slow; Pachyderm and the Google Model Card Toolkit are effectively finished.
- Consolidation (lakeFS+DVC, HF+Xet, CNCF ModelPack) points toward object-store-backed CAS plus OCI packaging as the 2026 direction; a flat-file registry that emits OCI-compatible digests and ModelPack-compatible `descriptor` fields will interoperate with that direction without adopting a registry server.

### Gaps
- Download counts (PyPI, Docker Hub) were not collected for any project; stars and release cadence are the only adoption proxies here.
- Enterprise adoption figures for lakeFS, KitOps and ModelPack beyond vendor statements were not found.
